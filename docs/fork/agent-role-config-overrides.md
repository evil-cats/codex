# Разрешённые переопределения конфигурации `agent role`

## Обзор

Доработка задаёт единый закрытый список настроек, которые `agent role` может
перенести из своего TOML-файла в конфигурацию создаваемого субагента. Эта карточка
является владельцем списка. Сейчас он расширяется ключом `model_context_window`:
его явное значение заменяет унаследованное значение родительской сессии только у
ребёнка.

## Зачем это нужно

`agent role` разбирается как полный `ConfigToml`, но ради сохранения полномочий и
предсказуемого наследования применяет только закрытый список разрешённых полей.
Этому списку нужен один владелец: последующие расширения профиля агента должны
проверяться и документироваться здесь, а не распределяться по несвязанным
карточкам.

Глобальный `model_context_window` действует на все модели. `agent role` уже может
выбрать отдельную модель и `model_reasoning_effort`, поэтому ей нужно такое же
узкое переопределение окна контекста без изменения конфигурации родителя и
остальных агентов.

## Карта файлов

| Файл | Роль |
| --- | --- |
| `codex-rs/core/src/agent/role.rs` | Включает `model_context_window` в разрешённую проекцию `agent role` и переносит его в итоговый `Config` |
| `codex-rs/core/src/agent/role_tests.rs` | Проверяет замену унаследованного значения и сохранение проецируемого слоя конфигурации |
| `codex-rs/core/tests/suite/subagent_notifications.rs` | Проверяет значение в конфигурации реально созданного субагента и неизменность родителя |

## Итоговый контракт

1. Полный TOML `agent role` не применяется к дочерней конфигурации напрямую:
   код времени выполнения переносит только поля из закрытого
   `AgentRoleOverrides`.
2. Новое разрешённое поле должно быть явно добавлено и в проекцию
   `AgentRoleOverrides`, и в материализацию итогового `Config`.

   Текущий закрытый список включает:

   - прямые переопределения `model`, `model_context_window`,
     `model_reasoning_effort`, `model_reasoning_summary`, `model_verbosity`,
     `personality` и `service_tier`;
   - инструкции модели и разработчика; контракт их файловых источников
     принадлежит отдельным карточкам `model-instructions-files.md` и
     `developer-instructions-files.md`;
   - только сужающие возможности значения `[features]` и `[skills]`, отобранные
     в `apply_role_to_config_inner`.

   Остальные поля `ConfigToml` не применяются к конфигурации субагента.
3. В TOML-файле `agent role` разрешён ключ верхнего уровня
   `model_context_window` с тем же типом и базовой семантикой, что в
   `ConfigToml`.
4. Явное значение роли заменяет унаследованный `model_context_window` только в
   конфигурации создаваемого субагента.
5. Если ключ в роли отсутствует, субагент сохраняет значение родительской
   конфигурации.
6. Проецируемый слой `SessionFlags` содержит применённое переопределение, чтобы
   итоговый `Config` и потребители слоёв конфигурации видели одно значение.
7. Доработка не меняет ограничение выбранной модели: существующий
   `models-manager` по-прежнему ограничивает запрошенное окно значением
   `max_context_window`.
8. Поле `spawn_agent`, отдельная глобальная настройка для каждой модели и
   конфигурация родительской сессии не меняются.

Пример роли:

```toml
model = "gpt-5.6-luna"
model_context_window = 800000
```

## Архитектурное решение

Файл роли разбирается как `ConfigToml`, после чего `apply_role_to_config_inner`
строит отдельный `AgentRoleOverrides`. Этот тип является закрытым списком и
владельцем границы: наличие поля в `ConfigToml` само по себе не даёт
`agent role` права менять соответствующую часть дочерней конфигурации.

Для `model_context_window` новый тип конфигурации не нужен. Значение копируется в
`AgentRoleOverrides`, сериализуется в проецируемый слой роли и явно присваивается
клону родительского `Config`.

Явное присваивание необходимо, потому что перестроение `ConfigLayerStack` само по
себе не обновляет уже материализованные поля клонированного `Config`. Проверка
предела остаётся в существующем `models-manager`, чтобы `agent role` не
дублировала ограничения выбранной модели.

## Порядок повторения при переносе

1. Найти `AgentRoleOverrides`, его заполнение из `ConfigToml` и
   `role_overrides::build_next_config`.
2. Для каждого нового поля отдельно решить, допустимо ли `agent role` изменять его
   без расширения полномочий родительской сессии.
3. Добавить разрешённое поле в закрытую сериализуемую проекцию и явно перенести
   его из разобранной конфигурации роли в клонированный `Config`.
4. Для `model_context_window` проверить, что отсутствие ключа сохраняет
   родительское значение, а явный ключ виден и в `Config`, и в
   `effective_config` проецируемого слоя.
5. В сквозном сценарии `spawn_agent` проверить замену значения только у дочерней
   сессии.
6. Не переносить сюда ограничение по выбранной модели: оно должно остаться в
   `models-manager`.

## Риски и ограничения

- Поле в `ConfigToml` нельзя считать автоматически разрешённым для `agent role`:
  каждое расширение закрытого списка требует отдельной проверки полномочий и
  наследования.
- Значение `model_context_window` роли не гарантирует фактическое окно указанного
  размера: итог ограничивается метаданными выбранной модели.
- Доработка намеренно не добавляет отдельный раздел каждой модели в глобальную
  конфигурацию и не делает `model_context_window` аргументом `spawn_agent`.
- Изменение способа материализации `Config` из слоя роли требует повторно
  проверить согласованность итогового поля и `effective_config`.
