# Внутренний workflow документации fork

## Обзор

Эта карточка фиксирует границу внутренней документации Hermione fork внутри
`docs/`, не превращая её в пользовательскую документацию upstream Codex.
Обязательные handoff-документы кодовых fork-доработок живут в `docs/fork/`;
прочие подкаталоги создаются только по необходимости и с понятным владельцем.

## Зачем это нужно

Правило upstream-репозитория в `AGENTS.md` запрещало широкую продуктовую и пользовательскую
документацию в `docs/`, потому что официальная документация Codex живет
отдельно. Hermione fork при этом нуждается во внутренней инженерной
документации: решениях, проверках, handoff, заметках сопровождения и учете
работы для fork-доработок.

Доработка уточняет правило: не добавлять широкую документацию продукта upstream,
но разрешить внутренние документы fork в `docs/` без обязательной привязки к
старым каталогам.

## Карта файлов

| Файл | Роль |
| --- | --- |
| `AGENTS.md` | Уточняет границу между документацией продукта upstream и внутренней документацией fork |
| `docs/fork/*.md` | Актуальные handoff-карточки fork-доработок |
| `docs/fork/migration/<version>.json` | Одноразовая машинная карта покрытия релизной миграции |
| `.codex/skills/fork/SKILL.md` | Назначает skill `fork` владельцем workflow внутренних fork-документов |
| `.codex/skills/fork/references/fork-card-contract.md` | Задаёт структуру и критерии готовности handoff-карточек |
| `.codex/skills/fork/assets/templates/fork-card.md` | Содержит шаблон новой handoff-карточки |
| `.codex/skills/fork/scripts/fork_cli.py` | Передаёт Markdown-файлы skill и `docs/fork/*.md` в markdownlint явными путями |
| `docs/.markdownlint-cli2.yaml` | Локальная markdownlint-конфигурация для внутренних документов |

## Итоговый контракт

1. `AGENTS.md` запрещает широкую продуктовую и пользовательскую документацию
   upstream Codex, но разрешает внутренние документы fork с решениями,
   проверками, заметками сопровождения, учётом работы и handoff.
2. Owner-карточки кодовых fork-доработок живут в `docs/fork/` и следуют
   контракту проектного skill `fork`.
3. Релизная миграция хранит одноразовые статусы в
   `docs/fork/migration/<version>.json`; owner-карточка не дублирует их.
4. Каталоги `docs/architecture`, `docs/plans`, `docs/follow-ups` и
   `docs/backlog` не обязательны. Новый каталог создаётся только из потребности
   текущей задачи и сразу получает назначение, навигацию, владельца и проверки.
5. Обычная проза и видимые заголовки пишутся по-русски; точные команды, пути,
   имена API и machine-readable значения enum сохраняют исходное написание.
6. Skill `fork` передаёт свои Markdown-файлы и `docs/fork/*.md` в markdownlint
   явными путями и использует локальную конфигурацию `docs/.markdownlint-cli2.yaml`.
   Проверка не должна зависеть только от globs и завершаться успешно с нулём
   проверенных файлов.

## Архитектурное решение

`AGENTS.md` задаёт границу разрешённой внутренней документации, skill `fork`
владеет форматом карточек, migration map и проверками, а локальная
markdownlint-конфигурация задаёт правила Markdown. Skill-owned CLI передаёт
Markdown-файлы явными путями, поэтому проверка карточек не зависит от globs по
умолчанию в конфигурации. Такое разделение не дублирует workflow в `AGENTS.md`:
owner-карточки хранят текущее устройство доработок, а статусы проходов, логи и
хронология остаются в migration map, skill-owned логах и Git.

## Порядок повторения при переносе

### 1. Обновить `AGENTS.md`

Сохранить запрет на широкую документацию продукта upstream, но добавить
исключение для внутренних документов fork в `docs/`.

### 2. Добавить локальную markdownlint-конфигурацию

Создать `docs/.markdownlint-cli2.yaml` с ограниченными globs по умолчанию и
настройками `MD013`. Убедиться, что skill-owned CLI передаёт Markdown-файлы
skill и `docs/fork/*.md` в markdownlint явными путями.

### 3. Синхронизировать fork handoff-карточки

Для кодовой fork-доработки:

- создать или обновить owner-карточку в `docs/fork/`;
- держать карточку синхронизированной с runtime-поведением, тестами,
  config/schema и prompts;
- для релизных миграций после отчета подагента обновлять машинный статус
  соответствующей записи `docs/fork/migration/<version>.json` через skill-owned
  `fork migration set-card-status`, не редактируя JSON вручную.

### 4. Создавать новые каталоги только при необходимости

Если будущей задаче нужен отдельный каталог `docs/architecture`, `docs/plans`,
`docs/follow-ups` или `docs/backlog`, создай его как часть этой задачи и
зафиксируй:

- назначение;
- индекс или навигационную запись;
- владельца и правила обновления;
- проверки или lint-маршрут;
- связь с `docs/fork/`.

Не восстанавливай отсутствующие каталоги механически во время миграции.

### 5. Синхронизировать индексы

После каждого перемещения, архивирования или обновления синхронизируй индекс
или migration-таблицу, которые указывают на измененный документ.

### 6. Сохранять правила языка

Выполнить редакторский проход:

- видимые заголовки и проза написаны по-русски;
- английский остается только для защищенных токенов;
- значения enum для статусов остаются английскими machine-readable значениями.

## Проверки

`manual-required`: это документационный workflow-контракт; его корректность
подтверждается редакторской сверкой `AGENTS.md`, skill `fork`, шаблона карточки,
явной передачи Markdown-путей в skill-owned CLI и локальной
markdownlint-конфигурации.

## Риски и ограничения

### Ограничения

- Не добавлять широкую документацию продукта upstream в `docs/`.
- Не считать owner-карточки доказательством конкретных запусков или статусов
  релизной миграции.
- Не пересоздавать `docs/architecture`, `docs/plans`, `docs/follow-ups` или
  `docs/backlog` без текущей задачи и владельца.
- Не утверждать, что markdownlint чист, если не проверены явные пути или globs.

### Риски

- Простой вызов markdownlint с конфигурацией может проверить ноль файлов;
  используй явные globs или прямые пути.
- Таблицы с `|` внутри фрагментов кода могут ломать разбор таблиц в
  markdownlint. Предпочитай списки значений enum через запятую в ячейках
  таблицы.
- Ссылки в reference-style могут стать неиспользуемыми после архивирования.
  После перемещений запускай lint и проверку ссылок.
- Legacy-документы могут расходиться с текущим checkout и не являются источником
  текущего контракта.
