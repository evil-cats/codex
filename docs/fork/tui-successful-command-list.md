# Список успешных команд в компактной TUI-группе

## Обзор

Эта карточка владеет fork-доработкой Hermione, которая сохраняет компактную
группировку последовательных успешных `exec`-команд под заголовком
`Ran N commands`, но показывает внутри группы сами команды с отображаемыми
аргументами. Обычная история TUI не показывает их `stdout` и `stderr`; полный
текст команд и вывод остаются доступны через `transcript` по `ctrl+t`.

## Зачем это нужно

В upstream Codex 0.153.0 каждая последовательная успешная команда снова
завершает отдельную ячейку истории вместе с предпросмотром её вывода:

```text
• Ran printf first
  └ first
• Ran printf second
  └ second
```

Hermione не принимает этот переход: она сохраняет наблюдаемость действий агента,
но оставляет последовательные успешные команды одной компактной группой без
`stdout` и `stderr` в обычной истории. Полный результат отдельного вызова
по-прежнему доступен через `transcript`:

```text
• Ran 3 commands · ctrl + t to view transcript
  ├ rg -n "pattern" docs/fork
  ├ git diff --check
  └ fork cards validate
```

## Итоговый контракт

- Последовательные успешные вызовы с источником `ExecCommandSource::Agent` или
  `ExecCommandSource::UnifiedExecStartup` продолжают объединяться в одну
  компактную ячейку истории.
- Заголовок сохраняет форму
  `Ran N command(s) · ctrl + t to view transcript` и фактическое количество
  успешных команд в начале группы.
- Сразу под заголовком TUI показывает каждую учтённую успешную команду в
  исходном порядке. Для нескольких команд используются ветви `├` и `└`; для
  единственной показанной команды используется `└`.
- Строка команды включает её отображаемые аргументы. Внутренняя оболочка
  `bash -lc` скрывается тем же способом, что и в существующем рендерере
  одиночной команды; подсветка shell-синтаксиса сохраняется.
- Длинная или многострочная команда переносится и ограничивается существующим
  TUI-контрактом продолжений команды. Если команда целиком не помещается,
  компактная история показывает явный маркер пропущенных строк, а полный текст
  остаётся в `transcript`.
- В компактном списке успешных команд не показываются `stdout`, `stderr`,
  `(no output)`, `exit_code` и `duration` отдельных команд.
- `transcript_lines()` не меняется: `ctrl+t` по-прежнему показывает полный
  текст каждой команды, доступный сохранённый вывод, `exit_code` и `duration`.
- Выполняющиеся, ошибочные, отклонённые и интерактивные вызовы вне успешного
  префикса продолжают отображаться отдельными строками через существующий
  рендерер. Их текущие подписи и предпросмотр вывода эта доработка не меняет.
- Группы `Exploring`/`Explored`, core tool activity, пользовательские
  shell-команды и hook activity не меняются.
- Граница `MAX_GROUPED_COMMANDS` остаётся равной 32. Upstream 0.153.0 удалил
  этот лимит вместе с накоплением успешных команд, поэтому fork сохраняет
  прежнюю границу явно. Доработка увеличивает высоту уже ограниченной группы,
  но не делает историю безграничной.

## Архитектурное решение

`ExecCell::compact_group_display_lines()` продолжает определять успешный префикс
группы по существующим условиям `source`, завершения и `exit_code == 0`. После
заголовка рендерер проходит по этому же срезу `ExecCall` и через
`command_text_display_lines()` строит для каждого вызова только представление
команды. Оставшаяся часть `self.calls` по-прежнему передаётся обычному рендереру
вызовов.

`command_text_display_lines()` владеет отображаемым текстом команды, подсветкой
shell-синтаксиса, переносом и ограничением продолжений. Её используют и рендерер
одиночной команды, и компактный список. Блок вывода остаётся только в
`command_call_display_lines()`; неоднозначного позиционного флага вроде
`include_output: bool` в интерфейсе нет.

Компактный рендерер добавляет структурные префиксы группы после переноса
команды. Для промежуточного элемента первая строка получает `"  ├ "`, а
продолжения — `"  │ "`; для последнего элемента используются `"  └ "` и
пробельный префикс продолжения. Это сохраняет визуальную принадлежность каждой
перенесённой строки своей команде и не смешивает её с выводом.

`ExecCell::add_call()` и `ExecCell::should_flush()` сохраняют накопление
последовательных успешных вызовов и ограничение группы. В upstream 0.153.0 эта
ветка удалена вместе с `MAX_GROUPED_COMMANDS`, поэтому при переносе её нужно
восстановить поверх актуального жизненного цикла `ExecCell`. Полный `transcript`
не меняется.

Завершённая успешная группа остаётся активной ячейкой до следующей смысловой границы.
`ChatWidget::flush_completed_command_activity()` фиксирует её перед модальным окном,
подтверждением, slash-командой, пользовательским вводом, отдельной ячейкой
истории, `UnifiedExecInteraction` и завершением turn. Эти вызовы нельзя удалять
вместе с upstream-реализацией немедленной фиксации: без них группа пересекает
следующий пользовательский или агентский блок и нарушает порядок истории.

Во время replay завершённые `Agent` и `UnifiedExecStartup` вызовы проходят через
тот же begin/end lifecycle, что и живые команды. Ошибка сначала завершает
предыдущую успешную группу. Неотслеженное завершение `UnifiedExecStartup` можно
присоединить к совместимой неактивной группе; остальные завершения без
отслеженного начала не должны вытеснять несвязанную активную ячейку.

## Порядок повторения при переносе

1. Проверить, накапливает ли актуальный upstream последовательные успешные
   `exec`-команды в одной `ExecCell`, и показывает ли обычная история их вывод.
2. Если upstream предоставляет эквивалентный список без вывода и сохраняет
   полный `transcript`, удалить fork-отрисовку, оставив регрессионное покрытие или
   признав карточку неприменимой.
3. Иначе восстановить условия выбора успешного префикса, правила накопления
   `ExecCall` и ограничение группы; не принимать отдельные ячейки с выводом как
   замену fork-контракта.
4. Сверить изменения жизненного цикла из upstream-коммита, который ввёл отдельные
   успешные ячейки, и восстановить `flush_completed_command_activity()` на
   смысловых границах модального окна, подтверждения, slash-команд, `replay` и
   завершения turn.
5. Выделить общее форматирование текста команды из рендерера одиночного вызова
   и переиспользовать его для вложенных строк компактной группы.
6. Не переносить рендеринг `CommandOutput` в компактный список. Проверить, что
   обычное представление не содержит вывода, а `transcript` содержит и команды, и
   доступный вывод.
7. Сохранить отдельное отображение выполняющихся, ошибочных, отклонённых и
   интерактивных вызовов, а также существующие группы `Exploring`/`Explored` и
   core tools.
8. Обновить снимки `insta` для видимого списка, переноса длинных команд и
   смешанного успешного/неуспешного жизненного цикла.

## Риски и ограничения

- Группа до `MAX_GROUPED_COMMANDS` теперь занимает до одной видимой строки на
  короткую команду вместо одной строки на всю группу. Это осознанный компромисс
  ради наблюдаемости; полный вывод по-прежнему не заполняет обычную историю.
- Ограничение продолжений означает, что очень длинные или многострочные команды
  могут отображаться не полностью. Маркер сокращения и `transcript`
  должны явно сохранять путь к полному представлению.
- Команда уже присутствует в TUI во время выполнения и в `transcript`; доработка
  делает её видимой также после успешного завершения, но не создаёт новый
  источник данных и не изменяет формат rollout.
- Не следует заменять список семантическими подписями вроде `Search` или `Read`:
  для этого существуют рендерер групп `Exploring`/`Explored` и отдельная
  карточка core tool activity. Компактная группа успешных команд показывает
  фактический текст команды.
