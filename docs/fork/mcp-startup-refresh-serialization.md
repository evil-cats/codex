# Согласование MCP при незавершённом запуске

## Обзор

Согласование переиспользует совместимое незавершённое MCP-соединение, не ждёт
рукопожатия, сразу публикует представление с актуальным фильтром инструментов и
не запускает второй сервер.

Если разделённый startup обычного MCP-сервера завершается `Failed`, worker
предварительного обновления помечает актуальный runtime грязным и выполняет одно
обычное согласование с заменой. Codex Apps использует собственное фоновое
переподключение и в этот механизм не входит.

Доработка относится только к первоначальному startup, обычному объединённому
refresh и замене после его первого отказа. Восстановлением уже работавшего
транспорта после `TransportClosed` или `BrokenPipe` владеет карточка
[`mcp-transport-recovery.md`](mcp-transport-recovery.md).

## Зачем это нужно

Инициализация MCP и уточнение эффективной конфигурации выполняются параллельно.
Совместимый refresh обязан сохранить общее рукопожатие, иначе один логический
запуск превращается в отмену и второй процесс. Если общее рукопожатие
завершается `Failed`, уже потреблённый dirty-state нужно создать повторно ровно
один раз, чтобы обычное согласование заменило непереиспользуемый клиент без
цикла повторов.

## Итоговый контракт

### Совместимый незавершённый startup

`McpConnectionSet::new` переиспользует только активный, неотменённый клиент с
незавершённым startup.
Для этого должны совпасть полная `McpServerConnectionIdentity`,
`catalog_item_limit` и эффективный режим протокола; отложенный или уже отменённый
startup не переиспользуется. Идентичность включает конфигурацию транспорта,
`environment_id`, значения указанных переменных окружения, идентичность
авторизации и кэша, `client_elicitation_capability`, клиентские расширения и
режим `agent_plugin`.

Фильтр инструментов и `tool_timeout` принадлежат новому `McpServerView`, поэтому
совместимое согласование может изменить видимый модели набор инструментов без
повторного рукопожатия. Изменение идентичности транспорта, ограничения выдачи
каталога или режима протокола создаёт новое соединение.

### Немедленное согласование и отмена

`Session::refresh_mcp_if_dirty` потребляет dirty-state и публикует желаемое
состояние, не ожидая незавершённый startup. Общий клиент остаётся тем же, а новый
набор соединений публикует его итог через собственный `McpStartupComplete`.
Несколько накопленных invalidation по-прежнему объединяются ограниченным каналом
prewarm и `McpRefresh`.

Если следующее согласование удаляет сервер, общее соединение отменяется после
освобождения всех владеющих представлений. Настоящий `Cancelled` при отключении,
shutdown, hard refresh или несовместимой замене не скрывается.

### Замена после `Failed`

Каждый набор соединений наблюдает только обычные MCP startup-клиенты, которые он
переиспользовал незавершёнными. Codex Apps исключён: его
`CodexAppsStartupReconnect` уже делает фоновое переподключение. Привязанный к
snapshot сигнал возвращает `true` только если хотя бы один наблюдаемый клиент
завершился `StartupOutcomeError::Failed`; `Ready` и `Cancelled` не требуют
замены.

`McpRuntime` принимает исход только от всё ещё актуального snapshot. Worker
предварительного обновления ждёт его без семафора refresh; новый запрос refresh
или изменение авторизации прерывает ожидание и немедленно запускает обычное
согласование. После общего `Failed` worker один раз помечает runtime грязным.
Следующее согласование уже не может переиспользовать клиент с исходом `Failed`
и создаёт замену.

Успешный разделённый startup не вызывает дополнительную публикацию. Замена,
которая сама завершилась ошибкой, не образует бесконечный цикл повторов, потому
что она не является переиспользованным pending startup нового snapshot.

Явный hard refresh через `replace_fresh`, shutdown и другие операции, которые
по контракту требуют свежих соединений или отмены работы, не превращаются в
coalesced refresh и не скрывают свои настоящие `Cancelled`.

## Архитектурное решение

Согласование переносит тот же `AsyncManagedClient` и
`Arc<McpServerConnection>` в новый `McpServerView`; `McpPublicationGate` и
`McpStartupComplete` остаются у каждого набора соединений. Отдельный координатор
запуска не добавляется, согласование не откладывается.

Сигнал отказа строится отдельным наблюдением уже общих futures. Он не запускает
клиент, не меняет владение отменой и не зависит от `tx_event` или
`EventMsg::McpStartupComplete`. `ReusedPendingStartupOutcome` различает
незавершённое наблюдение, завершение без `Failed` и сам исход `Failed`. Runtime
повторно проверяет указатель текущего опубликованного snapshot перед возвратом
результата.

## Порядок повторения при переносе

1. Найти предикат переиспользования pending startup и подтвердить полное
   сравнение идентичности соединения, `catalog_item_limit` и режима протокола.
2. Сохранить немедленное согласование без ожидания startup до
   `McpRefresh::claim`.
3. Сохранить наблюдатель только для `Failed` у реально переиспользованных
   клиентов с незавершённым startup.
4. Проверить актуальность snapshot перед созданием дополнительного invalidation.
5. Сохранить немедленную обработку новых запросов refresh, изменений
   авторизации и ограниченное объединение.
6. Не менять `rmcp-client`, восстановление транспорта, rollout, контекст модели,
   TUI, hard refresh и семантику shutdown.

## Риски и ограничения

- Переиспользование pending startup требует точной идентичности,
  ограничения каталога и режима протокола; несовместимое изменение намеренно
  создаёт новый процесс сервера.
- Наблюдатель отказа не считает `Cancelled` основанием для замены: удалённый или
  остановленный MCP-сервер не должен самовосстанавливаться.
- Новый запрос или изменение авторизации может заменить snapshot, пока worker
  ждёт исход. Runtime обязан отбросить результат старого snapshot.
- Доработка повторяет только первый общий startup с исходом `Failed` и не
  является сторожевым механизмом для повторных отказов, зависшего рукопожатия
  или отказа транспорта.
- `TransportClosed`, `broken pipe`, один повтор и ленивое восстановление после
  смерти idle transport остаются отдельным контрактом после startup и здесь не
  меняются.
