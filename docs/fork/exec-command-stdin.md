# Начальный `stdin` для `exec_command`

## Обзор

Эта карточка владеет доработкой fork Hermione, которая добавляет в основной инструмент
`exec_command` опциональный строковый аргумент `stdin`. Аргумент передаёт
процессу начальный текст напрямую через стандартный ввод и устраняет
необходимость создавать отдельную команду-производитель вроде `echo` или
`printf` только ради подачи данных в shell.

## Зачем это нужно

До этой доработки модель могла подать данные программе через конвейер команд shell:

```text
echo "hello" | wc -c
```

Однако парсер разрешений рассматривает конвейер как цепочку исполняемых команд.
В примере отдельно проверяются `echo` и `wc`, хотя пользовательское намерение
состоит в запуске одного потребителя `wc`, а `hello` является только входными
данными. При динамическом содержимом это создаёт повторяющиеся запросы разрешения
для синтетической команды-производителя и делает сохранённый `prefix_rule`
бесполезным для пакетной обработки разных входов.

`write_stdin` не является полноценной заменой:

- сначала требуется запустить долгоживущую сессию и получить `session_id`;
- без нового аргумента обычный non-TTY `exec_command` запускается с закрытым stdin;
- интерактивный PTY меняет терминальную семантику, включая построчную обработку,
  отображение введённых символов и управляющие символы;
- для потребителей, читающих поток до EOF, нужен явный конец входа, а не
  остающаяся открытой интерактивная сессия.

Новый аргумент позволяет выразить то же намерение без команды-производителя для shell:

```json
{
  "cmd": "wc -c",
  "stdin": "hello"
}
```

Ожидаемый stdout равен `5`: `exec_command` передаёт ровно пять UTF-8-байтов и
закрывает non-TTY stdin. Для поведения, эквивалентного `echo "hello"`, модель
явно передаёт `"hello\n"`, и ожидаемый stdout равен `6`.

протокола перемещены.

### Намеренно неизменяемые зоны

- `write_stdin` сохраняет контракт последующего взаимодействия с уже запущенной
  сессией и не становится обязательным промежуточным шагом для начального ввода;
- устаревший `shell_command` не получает новый аргумент;
- протокол `apply_patch` не расширяется начальным вводом через эту карточку;
- сбор вывода из stdout/stderr, усечение, сохранение вывода во внешний файл и
  `max_output_tokens` не меняются;
- профиль разрешений файловой системы и сети, а также правила
  привилегированного запуска не ослабляются;
- необработанный бинарный ввод, кодирование base64, потоковая передача больших
  файлов и передача файлового дескриптора не входят в область карточки.

## Итоговый контракт

### Спецификация инструмента

`exec_command` получает новое необязательное свойство:

```text
stdin?: string
```

Видимое модели описание должно сообщать:

1. Значение передаётся процессу как UTF-8 без неявного `\n`.
2. При `tty=false` после текста следует EOF.
3. При `tty=true` значение является начальными PTY-символами, а сессия
   остаётся доступной через `write_stdin`.
4. Параметр предназначен для данных, которые иначе пришлось бы подавать через
   отдельную команду-производитель или конвейер shell.

`stdin` не является обязательным полем. Отсутствие аргумента должно сохранять
прежнее поведение на уровне байтов и жизненного цикла.

### Кодирование и точность данных

- JSON-строка декодируется в Rust `String`, затем передаётся как UTF-8-байты;
- пустая строка допустима;
- `\n`, `\r`, NUL и другие допустимые символы JSON-строки передаются как байты
  после стандартного декодирования JSON;
- инструмент не добавляет разделитель, перевод строки или управляющий символ
  терминала;
- бинарные данные, для которых требуется сохранить произвольные октеты вне
  UTF-8, должны получить отдельный будущий контракт.

### Жизненный цикл без TTY

Если `tty=false` и `stdin` предоставлен:

1. Sandbox и проверка разрешения обрабатывают `cmd` обычным способом.
2. Процесс запускается с pipe для stdin.
3. Весь `stdin` передаётся в канал записи в исходном порядке.
4. Канал записи закрывается сразу после успешной передачи, поэтому
   процесс-потребитель видит EOF.
5. `exec_command` ожидает вывод или завершение до обычного `yield_time_ms`; если
   процесс продолжает работать после EOF, применяется прежний жизненный цикл
   сессии.

`stdin: ""` пропускает запись байтов, но всё равно открывает и закрывает pipe,
чтобы процесс получил пустой поток и EOF. Опущенный `stdin` не требует pipe и
сохраняет текущий путь запуска с закрытым stdin.

### Жизненный цикл с TTY

Если `tty=true` и `stdin` предоставлен:

- текст передаётся после успешного запуска PTY;
- stdin не закрывается автоматически;
- построчная обработка терминала может преобразовывать или буферизовать ввод;
- последующий `write_stdin` продолжает работать по обычному `session_id`;
- процесс-потребитель, которому нужен точный конечный поток и EOF, должен
  использовать `tty=false`.

### Ошибки и атомарность запуска

Если процесс не удалось запустить, `stdin` никуда не передаётся. Если процесс
запустился, но начальный ввод не удалось полностью принять:

- инструмент возвращает явную ошибку начального stdin;
- процесс завершается и удаляется из реестра процессов;
- команда не перезапускается автоматически, потому что она уже могла выполнить
  побочный эффект до ошибки записи;
- частичная запись не выдаётся за успешную передачу полного значения.

Для удалённого окружения клиент обязан проверить возможность `initial_stdin` до
запуска. Если она отсутствует, `exec_command` возвращает понятную ошибку
совместимости и не отправляет запрос со значением, которое старый exec-server
мог бы молча проигнорировать.

### Граница sandbox и проверки разрешений

`stdin` не должен участвовать в:

- разборе shell и разделении `cmd` по `|`, `&&`, `||`, `;` или границам
  подоболочки;
- `canonicalize_command_for_approval`;
- `UnifiedExecApprovalKey`;
- сопоставлении с `prefix_rule`;
- классификации безопасности команды;
- построении `hook_command` для обработчиков hook Bash;
- тексте команды в диалоге подтверждения.

Следовательно, вызов с `cmd: "wc -c"` и любым новым `stdin` использует то же
разрешение команды, что и `wc -c` без начального ввода. Содержимое не создаёт
синтетический сегмент `echo`/`printf` и не требует отдельного подтверждения.

Это не означает выполнение вне sandbox. Запущенный процесс получает те же
ограничения файловой системы и сети, а также те же дополнительные разрешения,
что и при вызове без `stdin`. Если программа интерпретирует вход как команды,
последствия этих команд всё равно ограничиваются sandbox процесса.

### Обработчики hook, события и сохранение данных

- Bash `PreToolUse` продолжает получать только `{"command": cmd}`;
- перезапись обработчиком hook может изменить `cmd`, но обязана сохранить
  исходный `stdin` без изменения;
- начальный ввод не создаёт отдельный `TerminalInteractionEvent`, потому что
  исходный вызов инструмента уже содержит значение;
- события начала и завершения команды продолжают описывать её жизненный цикл и
  не дублируют полный ввод;
- исходные аргументы инструмента, включая `stdin`, могут сохраняться в JSONL
  журнала выполнения и трассировках; параметр не является каналом для секретов.

Если `exec_command` перехвачен специальной веткой `apply_patch`, `stdin` нельзя
молча игнорировать. Текущая реализация должна вернуть понятную ошибку для этой
комбинации; расширение отдельного транспорта `apply_patch` принадлежит другому
решению.

## Архитектурное решение

### Передавать ввод как данные процесса

`stdin` проходит отдельным полем через аргументы инструмента, `ExecCommandRequest`,
`UnifiedExecRequest` и транспорт запуска процесса. Оно не преобразуется в
исходный текст shell и не встраивается в переменную окружения или argv.

Для прямого локального запуска диспетчер процессов открывает канал записи при
`stdin.is_some()`. Для удалённого запуска опциональный начальный ввод входит в
`ExecParams` exec-server и обрабатывается исполнителем сразу после запуска.
Такой путь сохраняет семантику конечного потока и позволяет серверу закрыть
канал записи без дополнительной гонки между `exec`, `process/write` и новым RPC.
Если удалённый запуск использует обратный вызов сетевой политики, core сначала
строит тот же `ExecParams` с `initial_stdin`, а затем передаёт его в
`start_with_network_policy_decider`; отдельная ветка не должна собирать или
терять параметры процесса заново.

### Проверка возможности удалённого окружения

`EnvironmentCapabilities` получает логическое поле `initial_stdin`. Новый
exec-server объявляет `true`; у старого сервера отсутствующее поле получает
значение `false`. Core проверяет эту возможность до удалённого запуска, если
`stdin` предоставлен.

Эта проверка требуется не для прямого локального запуска, а для защиты от тихой
потери данных при несовпадении версий клиента и exec-server.

### Идентичность разрешения остаётся основанной только на команде

Проверка разрешения отвечает на вопрос, какой процесс и с какими разрешениями
можно запустить. `stdin` является последующим вводом этого процесса и намеренно не
расширяет идентичность команды. Это позволяет повторно использовать разрешение
для одного потребителя с разными входными данными.

При этом общий интерпретатор вроде `bash`, `sh`, `python -` или PowerShell может
трактовать stdin как исполняемый исходный текст. Сохранённое разрешение для
такого общего интерпретатора остаётся опасным и не становится безопасным
благодаря этой доработке. Системный sandbox остаётся последней границей
последствий.

## Порядок повторения при переносе

Для нового checkout следующей версии upstream:

1. Найти текущие структуры-владельцы спецификации инструмента и десериализации для
   `exec_command`.
2. Проверить актуальный путь `ExecCommandArgs` до исполнителя unified exec и
   запуска локального или удалённого процесса.
3. Добавить опциональный `stdin` в схему инструмента и структуры запроса, не
   меняя обязательные поля и поведение по умолчанию.
4. Сохранить основанную только на команде идентичность разрешения, данные hook

5. Реализовать локальную начальную запись: открыть stdin только при
   необходимости, передать все байты и закрыть канал записи non-TTY.
6. Расширить протокол exec-server опциональным начальным вводом и проверкой

7. Реализовать начальную запись и закрытие на стороне сервера с одинаковым

8. Не допустить тихого игнорирования в специальной ветке перехвата `apply_patch`.
9. Добавить проверки спецификации, обработчика, транспорта процесса, возможности
   удалённого сервера, EOF, разрешений и sandbox.
10. Сверить итоговый diff с картой файлов, контрактом и действующими

## Проверки

Исполняемая карта card-level regression tests:

```json
{
  "schema": "fork-tests.v1",
  "tests": [
    {
      "purpose": "схема инструмента, обработчик, разрешения и сквозной контракт stdin",
      "argv": ["just", "test", "-p", "codex-core", "exec_command_stdin"]
    },
    {
      "purpose": "локальный и удалённый транспорт начального stdin в exec-server",
      "argv": ["just", "test", "-p", "codex-exec-server", "initial_stdin"]
    },
    {
      "purpose": "возможность протокола exec-server и сериализация",
      "argv": [
        "just",
        "test",
        "-p",
        "codex-exec-server-protocol",
        "initial_stdin"
      ]
    },
    {
      "purpose": "подтверждение начальной записи stdin в реализации PTY",
      "argv": ["just", "test", "-p", "codex-utils-pty", "initial_stdin"]
    },
    {
      "purpose": "Windows legacy и elevated runner: initial stdin, EOF и фактические ошибки WriteFile",
      "platforms": ["windows"],
      "argv": ["just", "test", "-p", "codex-windows-sandbox", "initial_stdin"]
    }
  ]
}
```

Windows-набор включает четыре прямых сценария:

- `initial_stdin_legacy_write_file_error_reaches_caller` возвращает вызывающему
  коду фактический `ERROR_BROKEN_PIPE` из legacy `WriteFile`;
- `initial_stdin_runner_merges_streaming_input_and_closes_on_eof` проверяет
  точный порядок `InitialStdin`, последующего `Stdin` и `CloseStdin`;
- `initial_stdin_runner_returns_reported_error` передаёт ошибку записи runner
  через реальный framed IPC и возвращает её вызывающему коду;
- `initial_stdin_result_preserves_runner_write_file_error` проверяет фактическую
  ошибку runner и её сериализацию в `InitialStdinResult`.

Эти модули собираются только при `target_os = "windows"`, поэтому запись карты
ограничена платформой `windows`. На Linux и macOS `fork tests` показывает
`skip-platform` и не считает запись ошибкой; на Windows она автоматически
становится обязательной. Пропуск не является доказательством Windows-сценариев
и остаётся явно видимым в результате запуска.

## Риски и ограничения

- `stdin` сохраняется в исходных аргументах инструмента и журнале rollout; секреты
  передавать через него нельзя без отдельного контракта редактирования.
- Большой текст увеличивает объём данных вызова инструмента и память процесса;
  отдельный контракт потокового или файлового ввода в первой версии отсутствует.
- Интерпретатор может выполнить stdin как исходный текст программы. Проверка
  разрешения только по команде не анализирует этот текст; сохранённое разрешение общих
  интерпретаторов требует особой осторожности.
- PTY не гарантирует точного на уровне байтов терминального поведения; точный
  конечный ввод требует `tty=false`.
- Несовпадение версий удалённого exec-server должно обнаруживаться проверкой
  возможности `initial_stdin`, иначе существует риск тихой потери ввода.
- Новая ветка удалённой диспетчеризации (например, обратный вызов сетевой
  политики) может обойти начальный ввод, если заново собирает `ExecParams`; обе
  ветки должны получать одну структуру, сформированную до выбора способа запуска.
- Ошибка после частичной записи не может отменить уже выполненные процессом
  действия; поэтому автоматический повтор запрещён.
- Ввод не отображается в диалоге разрешения команды. Пользователь подтверждает
  исполняемый файл и разрешения, а не каждое значение ввода.
