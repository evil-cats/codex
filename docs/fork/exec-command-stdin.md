# Начальный `stdin` для `exec_command`

## Обзор

Эта карточка владеет доработкой fork Hermione, которая добавляет в основной инструмент
`exec_command` опциональный строковый аргумент `stdin`. Аргумент передаёт
процессу начальный текст напрямую через стандартный ввод и устраняет
необходимость создавать отдельную команду-производитель вроде `echo` или
`printf` только ради подачи данных в shell. Карточка также фиксирует проверку
начального ввода при рискованных полномочиях и сохраняемую для `resume` запись
фактически переданного `stdin` в пользовательском транскрипте.

## Зачем это нужно

До этой доработки модель могла подать данные программе через конвейер команд shell:

```text
echo "hello" | wc -c
```

Однако парсер разрешений рассматривает конвейер как цепочку исполняемых команд.
В примере отдельно проверяются `echo` и `wc`, хотя пользовательское намерение
состоит в запуске одного потребителя `wc`, а `hello` является только входными
данными. При динамическом содержимом это создаёт повторяющиеся запросы разрешения
для синтетической команды-производителя и делает сохранённый `prefix_rule`
бесполезным для пакетной обработки разных входов.

`write_stdin` не является полноценной заменой:

- сначала требуется запустить долгоживущую сессию и получить `session_id`;
- без нового аргумента обычный non-TTY `exec_command` запускается с закрытым stdin;
- интерактивный PTY меняет терминальную семантику, включая построчную обработку,
  отображение введённых символов и управляющие символы;
- для потребителей, читающих поток до EOF, нужен явный конец входа, а не
  остающаяся открытой интерактивная сессия.

Новый аргумент позволяет выразить то же намерение без команды-производителя для shell:

```json
{
  "cmd": "wc -c",
  "stdin": "hello"
}
```

Ожидаемый stdout равен `5`: `exec_command` передаёт ровно пять UTF-8-байтов и
закрывает non-TTY stdin. Для поведения, эквивалентного `echo "hello"`, модель
явно передаёт `"hello\n"`, и ожидаемый stdout равен `6`.

Отдельное поле данных не гарантирует, что потребитель не исполнит его как код.
`wc` считает байты, но `bash`, `python -`, SQL-клиент или интерактивный REPL
могут интерпретировать ту же строку как действие. Поэтому начальный `stdin` не
должен обходить approval, который upstream применяет к непустому `write_stdin`
при `strict review` и для процессов с расширенными полномочиями.

Пользовательский транскрипт должен отличать запрошенный вызов инструмента от
подтверждённой передачи. Исходные `arguments` в rollout показывают намерение
модели, но только успешная запись `stdin` доказывает взаимодействие с процессом.

Удалённый запуск использует отдельную диспетчеризацию для обратных вызовов
сетевой политики. Вместе с владельцами карточки нужно проверять всю цепочку:

- `codex-rs/exec-server/src/process.rs` — оба метода `ExecBackend::start` и
  `ExecBackend::start_with_network_policy_decider` принимают один и тот же
  `ExecParams`;
- `codex-rs/exec-server/src/remote_process.rs` — передаёт `ExecParams` клиенту
  без реконструкции при обоих вариантах запуска;
- `codex-rs/exec-server/src/client.rs` — отправляет полученный `ExecParams` в
  `exec` RPC и отдельно регистрирует контроллер сетевой политики;
- `codex-rs/utils/pty/src/process.rs` — при построении `ProcessHandle` сохраняет
  одновременно подтверждаемый `initial_stdin_tx` и признак Windows `tty`,
  определяющий семантику прерывания.

Карта сверена с фактическими изменениями реализации. Неблокирующий Unix
PTY-драйвер находится в `codex-rs/utils/pty/src/unix_io.rs`. Устаревший
обработчик `shell` отсутствует и не является владельцем контракта этой карточки.
При переносе на новую версию upstream карту нужно сверять заново, если транспорт
процесса или литералы протокола перемещены.

В `rust-v0.152.0` upstream-проверки последующего `write_stdin` объединены с
fork-политикой начального ввода: NUL и предел полного сериализованного действия
проверяет общий `validate_terminal_input_review` в `Session::request_approval`, а
сравнение сохранённых полномочий терминала остаётся в `TerminalPermissions`.

В `rust-v0.153.0` upstream сам показывает в TUI полный переданный ввод в текущей
сессии. Fork использует это полное отображение, но сохраняет прежний точный
заголовок `Interacted with terminal`, начальный `exec_command.stdin`, отдельную
проверку до запуска, подтверждаемую полную передачу, отдельную сохраняемую
rollout-запись, `ThreadItem::TerminalInteraction` и восстановление
подтверждённого ввода при `resume`; исходные `FunctionCall.arguments` по-прежнему
не считаются доказательством передачи.

### Намеренно неизменяемые зоны

- `write_stdin` остаётся механизмом последующего взаимодействия с уже
  запущенной сессией и не становится обязательным промежуточным шагом для
  начального ввода; его успешно переданные данные входят в общий контракт
  сохраняемого транскрипта;
- устаревший `shell_command` не получает новый аргумент;
- протокол `apply_patch` не расширяется начальным вводом через эту карточку;
- сбор вывода из stdout/stderr, усечение, сохранение вывода во внешний файл и
  `max_output_tokens` не меняются;
- профиль разрешений файловой системы и сети, а также правила
  привилегированного запуска не ослабляются;
- необработанный бинарный ввод, кодирование base64, потоковая передача больших
  файлов и передача файлового дескриптора не входят в область карточки.

## Итоговый контракт

### Спецификация инструмента

`exec_command` получает новое необязательное свойство:

```text
stdin?: string
```

Видимое модели описание должно сообщать:

1. Значение передаётся процессу как UTF-8 без неявного `\n`.
2. При `tty=false` после текста следует EOF.
3. При `tty=true` значение является начальными PTY-символами, а сессия
   остаётся доступной через `write_stdin`.
4. Параметр предназначен для данных, которые иначе пришлось бы подавать через
   отдельную команду-производитель или конвейер shell.

`stdin` не является обязательным полем. Отсутствие аргумента должно сохранять
прежнее поведение на уровне байтов и жизненного цикла.

### Кодирование и точность данных

- JSON-строка декодируется в Rust `String`, затем передаётся как UTF-8-байты;
- пустая строка допустима;
- `\n`, `\r`, NUL и другие допустимые символы JSON-строки передаются как байты
  после стандартного декодирования JSON, если содержимое не требует проверки;
- NUL в требующем проверки вводе отклоняется до запуска, потому что рендерер
  approval не может представить его проверяющему без потери точности;
- инструмент не добавляет разделитель, перевод строки или управляющий символ
  терминала;
- бинарные данные, для которых требуется сохранить произвольные октеты вне
  UTF-8, должны получить отдельный будущий контракт.

### Жизненный цикл без TTY

Если `tty=false` и `stdin` предоставлен:

1. Sandbox и идентичность разрешения команды обрабатывают `cmd` обычным
   способом, а политика содержимого при необходимости проверяет полный `stdin`
   до запуска.
2. После положительного решения процесс запускается с pipe для stdin.
3. Весь `stdin` передаётся в канал записи в исходном порядке.
4. После подтверждения полной передачи непустого `stdin` создаётся сохраняемая
   запись взаимодействия с терминалом.
5. Канал записи закрывается сразу после успешной передачи, поэтому
   процесс-потребитель видит EOF.
6. `exec_command` ожидает вывод или завершение до обычного `yield_time_ms`; если
   процесс продолжает работать после EOF, применяется прежний жизненный цикл
   сессии.

`stdin: ""` пропускает запись байтов, но всё равно открывает и закрывает pipe,
чтобы процесс получил пустой поток и EOF. Опущенный `stdin` не требует pipe и
сохраняет текущий путь запуска с закрытым stdin.

Если управляемые требования отключают возобновляемый unified exec, одноразовый
`exec_command` сохраняет то же поле `stdin` в `ExecCommandRequest`, принудительно
использует non-TTY-путь и передаёт запрос через `exec_command_to_completion`.
Его видимая модели схема не предлагает `tty` или `write_stdin` и прямо сообщает,
что после начального текста процесс получает EOF.

### Жизненный цикл с TTY

Если `tty=true` и `stdin` предоставлен:

- полный текст, требующий проверки, проверяется до запуска PTY;
- текст передаётся после успешного запуска PTY;
- после подтверждения полной передачи непустого `stdin` создаётся сохраняемая
  запись взаимодействия с терминалом;
- stdin не закрывается автоматически;
- построчная обработка терминала может преобразовывать или буферизовать ввод;
- последующий `write_stdin` продолжает работать по обычному `session_id`;
- процесс-потребитель, которому нужен точный конечный поток и EOF, должен
  использовать `tty=false`.

### Ошибки и атомарность запуска

Если approval отклонён либо ввод нельзя полностью и без потерь представить
проверяющему, процесс не запускается и `stdin` никуда не передаётся. Если
процесс запустился, но начальный ввод не удалось полностью принять:

- инструмент возвращает явную ошибку начального stdin;
- процесс завершается и удаляется из реестра процессов;
- команда не перезапускается автоматически, потому что она уже могла выполнить
  побочный эффект до ошибки записи;
- частичная запись не выдаётся за успешную передачу полного значения;
- транскрипт не должен показывать полное значение как успешно переданное;
  ошибка обязана сохранить различие между попыткой и подтверждённой передачей.

Для удалённого окружения клиент обязан проверить возможность `initial_stdin` до
запуска. Если она отсутствует, `exec_command` возвращает понятную ошибку
совместимости и не отправляет запрос со значением, которое старый exec-server
мог бы молча проигнорировать.

### Граница sandbox и проверки разрешений

Идентичность разрешения команды и проверка конкретного содержимого `stdin`
являются разными решениями. `stdin` не участвует в:

- разборе shell и разделении `cmd` по `|`, `&&`, `||`, `;` или границам
  подоболочки;
- `canonicalize_command_for_approval`;
- `UnifiedExecApprovalKey`;
- сопоставлении с `prefix_rule`;
- классификации безопасности команды;
- построении `hook_command` для обработчиков hook Bash.

Поэтому вызов с `cmd: "wc -c"` и новым `stdin` использует ту же идентичность
разрешения команды, что и `wc -c` без начального ввода. Содержимое не создаёт
синтетический сегмент `echo`/`printf`, а разные данные не создают разные
`prefix_rule`.

При этом полный непустой начальный `stdin` обязан войти в `approval action`, если
выполняется хотя бы одно условие:

- запуск команды уже требует ручной либо автоматической проверки;
- действует `strict auto-review`;
- фактический запуск использует `elevated` или дополнительные полномочия, даже
  если решение о разрешении самой команды уже сохранено.

Проверка применяется ко всей строке независимо от программы и внешнего вида
данных. Реализация не пытается распознать shell-код, SQL, команды REPL или иной
«исполнимый» ввод: смысл данных зависит от состояния потребителя и не может быть
надёжно классифицирован по `cmd` и строке.

Проверка является реальным барьером, а не только визуализацией:

- пользователь или Guardian получает полный начальный `stdin` вместе с
  фактическими полномочиями и командой;
- положительное решение должно предшествовать запуску процесса и передаче
  любых байтов;
- сохранённое разрешение команды не заменяет проверку содержимого для режимов
  `elevated`, `additional` или `strict`;
- если сериализованный `approval action` вместе с `reason` превышает `8_000`
  байт, содержит NUL либо форматтер вынужден его усечь, запуск отклоняется
  целиком;
- усечённый prefix нельзя проверять и затем дополнять непроверенным хвостом.

Если запуск команды разрешён без проверки в стандартном sandbox-режиме и
`strict auto-review` не действует, дополнительная проверка содержимого не
создаётся. В таком пути сохраняются точная передача UTF-8, допустимый NUL и
прежняя семантика больших значений. Sandbox процесса остаётся границей
последствий, если потребитель интерпретирует вход как команды.

### Обработчики hook, события и сохранение данных

- Bash `PreToolUse` продолжает получать только `{"command": cmd}`;
- перезапись обработчиком hook может изменить `cmd`, но обязана сохранить
  исходный `stdin` без изменения;
- проверка содержимого получает полный `stdin` через `approval action`
  независимо от содержащей только команду полезной нагрузки хука Bash;
- после подтверждённой полной передачи непустого начального `stdin` создаётся
  отдельная запись взаимодействия с терминалом с уникальным идентификатором и
  ссылкой на исходный вызов `exec`;
- успешный непустой `write_stdin` создаёт такую запись сразу после подтверждения
  полной передачи, даже если последующая проверка состояния процесса завершится
  ошибкой;
- подтверждённое взаимодействие сохраняется как отдельная запись rollout, а
  app-server формирует из неё отдельный `ThreadItem` в исходном хронологическом
  порядке;
- текущий путь и replay используют одну ячейку истории TUI; после `resume`
  восстанавливаются как начальный `stdin`, так и последующий `write_stdin`;
- старые rollout-события `TerminalInteraction` без поля `id` получают при
  replay детерминированный идентификатор из `call_id` и позиции записи;
- отклонённый approval, ошибка запуска и неподтверждённая полная передача не
  создают ложную запись об успешном взаимодействии;
- исходный `FunctionCall` с аргументом `stdin` сохраняется отдельно как
  намерение модели и не используется сам по себе как доказательство передачи;
- сохраняемое взаимодействие является записью пользовательской истории и не
  добавляется в видимый модели контекст;
- исходные аргументы и подтверждённое взаимодействие могут содержать одно и то
  же значение в JSONL; `stdin` не является каналом для секретов.

Если `exec_command` перехвачен специальной веткой `apply_patch`, `stdin` нельзя
молча игнорировать. Текущая реализация должна вернуть понятную ошибку для этой
комбинации; расширение отдельного транспорта `apply_patch` принадлежит другому
решению.

## Архитектурное решение

### Передавать ввод как данные процесса

`stdin` проходит отдельным полем через аргументы инструмента, `ExecCommandRequest`,
`UnifiedExecRequest` и транспорт запуска процесса. Оно не преобразуется в
исходный текст shell и не встраивается в переменную окружения или argv.

Для прямого локального запуска диспетчер процессов открывает канал записи при
`stdin.is_some()`. Для удалённого запуска опциональный начальный ввод входит в
`ExecParams` exec-server и обрабатывается исполнителем сразу после запуска.
Такой путь сохраняет семантику конечного потока и позволяет серверу закрыть
канал записи без дополнительной гонки между `exec`, `process/write` и новым RPC.
Если удалённый запуск использует обратный вызов сетевой политики, core сначала
строит тот же `ExecParams` с `initial_stdin`, а затем передаёт его в
`start_with_network_policy_decider`; отдельная ветка не должна собирать или
терять параметры процесса заново.

### Проверка возможности удалённого окружения

`EnvironmentCapabilities` получает логическое поле `initial_stdin`. Новый
exec-server объявляет `true`; у старого сервера отсутствующее поле получает
значение `false`. Core проверяет эту возможность до удалённого запуска, если
`stdin` предоставлен.

Эта проверка требуется не для прямого локального запуска, а для защиты от тихой
потери данных при несовпадении версий клиента и exec-server.

### Начальный `stdin` не входит в идентичность разрешения

Проверка разрешения отвечает на вопрос, какой процесс, в каком окружении и с
какими разрешениями можно запустить. Текущий `UnifiedExecApprovalKey` учитывает
`environment_id`, `executable`, `command`, `cwd`, TTY и разрешения, но намеренно
не включает `stdin`. Это позволяет повторно использовать одно разрешение для
одного потребителя с разными входными данными.

Повторное использование разрешения команды не отменяет независимую проверку
содержимого. В режимах `elevated`, `additional` или `strict` каждое новое
непустое значение проверяется до запуска, даже если та же идентичность команды
уже разрешена.

### Проверка по полномочиям, а не по синтаксису

Общий интерпретатор вроде `bash`, `sh`, `python -`, PowerShell, SQL-клиент или
REPL может трактовать `stdin` как исполняемый текст. Другой потребитель считает
те же байты обычными данными. Проверка известных имён исполняемых файлов или
синтаксиса не даёт надёжной границы и легко обходится через состояние уже
запущенной программы.

Поэтому общий обработчик политики принимает решение по фактическим полномочиям
и `strict review`, а не по попытке классифицировать содержимое. Тот же принцип
применяется к начальному `stdin` до запуска и к последующему `write_stdin` после
запуска. Стандартный sandbox-режим остаётся границей последствий для пути без
проверки.

### Сохраняемый транскрипт

Исходный `FunctionCall` в rollout отвечает на вопрос, что модель запросила. Он
не доказывает, что approval был получен, процесс запущен и `stdin` полностью
принят. Поэтому `resume` не должен синтезировать успешное взаимодействие только
из `arguments` вызова инструмента.

Подтверждённая полная передача непустого ввода создаёт отдельную сохраняемую
запись взаимодействия, которая содержит:

- устойчивый уникальный ID конкретной передачи;
- ссылку на исходный вызов `exec`;
- `process_id`;
- точную строку `stdin`.

Подсистема хранения rollout сохраняет взаимодействие, история thread в
app-server восстанавливает его в исходном хронологическом месте, а replay TUI
использует тот же рендерер, что и уведомление в текущей сессии. Это правило
общее для начального `stdin` и `write_stdin`. Взаимодействие остаётся записью
пользовательской истории, не превращается в `ResponseItem` и не попадает в
видимый модели контекст.

## Порядок повторения при переносе

Для нового checkout следующей версии upstream:

1. Найти текущие структуры-владельцы спецификации инструмента и десериализации
   для `exec_command`.
2. Проверить актуальный upstream-путь approval для `write_stdin`: сохранённые
   полномочия запуска, `strict auto-review`, полное проверяемое действие, NUL,
   предел `8_000` байт и запрет исполнения непроверенного хвоста.
3. Проверить актуальный путь `ExecCommandArgs` до интерактивного и управляемого
   одноразового исполнителей unified exec, а затем до запуска локального или
   удалённого процесса.
4. Добавить опциональный `stdin` в схему инструмента и структуры запроса, не
   меняя обязательные поля и поведение по умолчанию.
5. Сохранить основанную только на команде идентичность разрешения, данные hook и
   сопоставление с `prefix_rule`, но вынести общую для начального `stdin` и
   `write_stdin` проверку содержимого.
6. До запуска передать полный начальный `stdin` в `approval action`, если
   требуется проверка команды, действует `strict auto-review` либо используются
   полномочия `elevated` или `additional`. Не считать закешированное разрешение
   команды разрешением нового содержимого.
7. Отклонять требующий проверки NUL, усечённый вывод форматтера и действие с
   `reason` больше `8_000` байт до запуска и без передачи байтов.
8. Реализовать локальную начальную запись: открыть stdin только при
   необходимости, передать все байты, получить подтверждение полной записи и
   закрыть канал записи non-TTY.
9. Расширить протокол exec-server опциональным начальным вводом и проверкой
   возможности; старый удалённый сервер должен давать явную ошибку совместимости
   до запуска. Если актуальный upstream выбирает между обычным запуском и
   `start_with_network_policy_decider`, сформировать `ExecParams` до выбора ветки
   и передать его без реконструкции.
10. Реализовать начальную запись и закрытие на стороне сервера с одинаковым
   поведением на Linux, macOS и Windows.
11. После подтверждённой передачи непустого ввода создать сохраняемую запись
    взаимодействия с терминалом с уникальным ID и ссылкой на родительский вызов
    `exec`, сохранить её в rollout и представить отдельным `ThreadItem` в
    исходном хронологическом порядке для текущего пути и replay TUI. Не выводить
    успех из исходных `arguments` вызова `FunctionCall` и не добавлять
    взаимодействие модели.
12. Не допустить тихого игнорирования в специальной ветке перехвата
    `apply_patch`.
13. Добавить проверки спецификации, обработчика, транспорта процесса,
    возможности удалённого сервера, EOF, approval до запуска, границ проверки,
    сохранения в rollout, replay app-server, транскрипта TUI, разрешений и
    sandbox. Перегенерировать схему app-server через принадлежащий skill
    генератор.
14. Сверить итоговый diff с картой файлов, контрактом и действующими
    ограничениями.

```json
      "purpose": "отсутствие непреднамеренных изменений snapshots взаимодействия с терминалом в TUI",
      "argv": [
        "cargo",
        "insta",
        "pending-snapshots",

```

Дополнительно обязателен `fork generators`, поскольку сохраняемое взаимодействие
с терминалом расширяет `ThreadItem` app-server v2 и артефакты схемы.

Windows-набор включает четыре прямых сценария:

- `initial_stdin_legacy_write_file_error_reaches_caller` возвращает вызывающему
  коду фактический `ERROR_BROKEN_PIPE` из legacy `WriteFile`;
- `initial_stdin_runner_merges_streaming_input_and_closes_on_eof` проверяет
  точный порядок `InitialStdin`, последующего `Stdin` и `CloseStdin`;
- `initial_stdin_runner_returns_reported_error` передаёт ошибку записи runner
  через реальный framed IPC и возвращает её вызывающему коду;
- `initial_stdin_result_preserves_runner_write_file_error` проверяет фактическую
  ошибку runner и её сериализацию в `InitialStdinResult`.

Эти модули собираются только при `target_os = "windows"`, поэтому запись карты
ограничена платформой `windows`. На Linux и macOS `fork tests` показывает
`skip-platform` и не считает запись ошибкой; на Windows она автоматически
становится обязательной. Пропуск не является доказательством Windows-сценариев
и остаётся явно видимым в результате запуска.

## Риски и ограничения

- `stdin` сохраняется в исходных аргументах инструмента и подтверждённой записи
  взаимодействия; секреты передавать через него нельзя без отдельного контракта
  редактирования.
- Большой текст увеличивает объём вызова инструмента, память процесса, rollout и
  транскрипт TUI; отдельный контракт потокового или файлового ввода отсутствует.
- Интерпретатор может выполнить `stdin` как исходный текст программы. Реализация
  намеренно не угадывает исполнимость: пути `elevated`, `additional` и `strict`
  проверяют полный ввод независимо от синтаксиса.
- Стандартный sandbox-режим без `strict review` не получает отдельную проверку
  содержимого; sandbox остаётся границей последствий такого запуска.
- Требующий проверки ввод не поддерживает NUL и обязан целиком вместе с `reason`
  для approval помещаться в `8_000` байт без усечения форматтером.
- PTY не гарантирует точного на уровне байтов терминального поведения; точный
  конечный ввод требует `tty=false`.
- Несовпадение версий удалённого exec-server должно обнаруживаться проверкой
  возможности `initial_stdin`, иначе существует риск тихой потери ввода.
- Новая ветка удалённой диспетчеризации (например, обратный вызов сетевой
  политики) может обойти начальный ввод, если заново собирает `ExecParams`; обе
  ветки должны получать одну структуру, сформированную до выбора способа запуска.
- Ошибка после частичной записи не может отменить уже выполненные процессом
  действия; поэтому автоматический повтор запрещён.
- Исходные `arguments` вызова `FunctionCall` нельзя считать доказательством
  передачи при `resume`; транскрипт восстанавливается только из подтверждённой
  сохраняемой записи.
- Сохраняемое взаимодействие с терминалом является поверхностью пользовательской
  истории и не должно добавлять повторный `stdin` в видимый модели контекст.
