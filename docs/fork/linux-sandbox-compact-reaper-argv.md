# Компактный `argv` PID-1 reaper в Linux sandbox

## Обзор

Эта карточка владеет доработкой fork Hermione, которая сохраняет добавленный
upstream процесс PID 1 для сбора осиротевших потомков Linux sandbox, но заменяет
его объёмную командную строку компактным внутренним режимом reaper. Во время
обычного выполнения команды `ps` и `/proc/1/cmdline` больше не показывают в
долгоживущем процессе сериализованный `PermissionProfile`, shell snapshot
bootstrap и полный текст запускаемой команды.

## Зачем это нужно

Upstream Codex `0.149.0` перевёл внутренний `codex-linux-sandbox` в режим
Bubblewrap `--as-pid-1`. Helper применяет ограничения, создаёт дочерний процесс
для команды, пересылает ему сигналы и вызывает `waitpid(-1)` для завершившихся
потомков. Это исправляет сбор осиротевших процессов, но оставляет исходный
`argv` helper на всё время работы команды.

В `rust-v0.153.2` upstream сохраняет эту схему работы без компактного self-`exec`:
цикл `waitpid(-1)` по-прежнему выполняется исходным helper. Поэтому fork-доработка
остаётся применимой и владеет заменой только долгоживущего reaper, не меняя
контракт upstream по сбору потомков.

Исходный `argv` содержит полный JSON профиля файловых и сетевых разрешений, а
для shell-команд также развёрнутую программу загрузки shell snapshot и
восстановления runtime-, proxy- и CA-переменных. Эти данные не нужны reaper после
запуска дочернего процесса и создают шумную, трудно читаемую строку в списке
процессов.

## Итоговый контракт

- В Bubblewrap inner stage `codex-linux-sandbox` остаётся PID 1 и продолжает
  собирать завершившихся осиротевших потомков.
- После `fork` основной команды PID 1 заменяет собственный процесс через
  self-`exec` на компактный внутренний режим, содержащий в `argv` только имя
  helper, маркер режима и PID основной команды.
- Компактный `argv` PID 1 не содержит `PermissionProfile`, shell snapshot
  bootstrap и текст пользовательской команды.
- Self-`exec` не меняет PID, родительскую связь с основной командой, применённые
  ограничения, файловый и сетевой sandbox.
- Сигналы `SIGHUP`, `SIGINT`, `SIGQUIT` и `SIGTERM` продолжают пересылаться
  основной команде и её process group.
- Exit status или завершающий сигнал основной команды возвращается вызывающему
  процессу без изменения.
- Если подготовить или выполнить компактный self-`exec` невозможно, helper
  использует прежний in-process reaper. Ошибка косметической оптимизации не
  должна отменять уже запущенную пользовательскую команду.
- Legacy Landlock и пути с прямым `exec` не меняются.

## Архитектурное решение

Новый lifecycle изолирован в дочернем модуле `namespace_reaper`, потому что
`linux_run_main.rs` уже является крупным orchestration-модулем. Inner stage до
применения ограничений сохраняет путь текущего executable, затем применяет
прежний профиль и передаёт выполнение модулю reaper.

Перед `fork` helper блокирует пересылаемые сигналы. Дочерний процесс
восстанавливает прежнюю маску и выполняет пользовательскую команду. Родительский
PID 1 вызывает тот же executable с `argv[0]`, равным
`codex-linux-sandbox`, и закрытым внутренним аргументом режима. `exec` заменяет
исходный address space и `/proc/1/cmdline`, сохраняя PID и дочерние процессы.

Повторно запущенный reaper принимает только точную внутреннюю форму аргументов и
проверяет, что работает как PID 1. Он устанавливает обработчики сигналов до их
разблокировки, затем вызывает `waitpid(-1)` и завершает процесс со статусом
основной команды. При неуспешном self-`exec` исходный процесс продолжает тот же
цикл ожидания без изменения пользовательского результата.

Изменение только `PR_SET_NAME` не подходит: оно меняет `comm`, но не содержимое
`/proc/PID/cmdline`. Ручное затирание памяти исходного `argv` не используется,
поскольку зависит от низкоуровневого расположения `argv` и `environ`.

## Порядок повторения при переносе

1. Проверить, сохраняет ли актуальный upstream `codex-linux-sandbox` как PID 1
   после запуска основной команды.
2. Найти текущую ветку Bubblewrap inner stage, которая применяет ограничения,
   выполняет `fork` и вызывает `waitpid(-1)`.
3. Если upstream уже заменяет долгоживущий `argv` компактным процессом, удалить
   fork-реализацию и сохранить регрессионную проверку либо признать карточку
   неприменимой.
4. Иначе подключить внутренний режим reaper до обычного разбора CLI и выполнить
   self-`exec` PID 1 после `fork` основной команды.
5. Сохранить прежние правила блокировки и пересылки сигналов, сбор всех
   завершившихся потомков и точное преобразование wait status в exit status.
6. Сохранить безопасный in-process fallback при ошибке подготовки или запуска
   self-`exec`.
7. Проверить фактический `/proc/1/cmdline`, status основной команды, пересылку
   сигналов и сбор осиротевшего потомка.

## Проверки

Исполняемая карта card-level regression tests:

```json
{
  "schema": "fork-tests.v1",
  "tests": [
    {
      "purpose": "компактный argv, self-exec fallback, exit status и сбор потомков namespace reaper",
      "argv": ["just", "test", "-p", "codex-linux-sandbox", "namespace_reaper"]
    },
    {
      "purpose": "пересылка сигналов основной команде sandbox",
      "argv": [
        "just",
        "test",
        "-p",
        "codex-linux-sandbox",
        "bwrap_signal_forwarder"
      ]
    }
  ]
}
```

Тест `compact_self_exec_failure_falls_back_without_cancelling_command` запускает
отдельную копию тестового бинарника и передаёт настоящему `run_command` путь к
заведомо отсутствующему исполняемому файлу reaper. Уже запущенная основная команда
записывает маркер и завершается с кодом `37`; внешний процесс должен увидеть и
маркер, и тот же код. Так тест наблюдает реальный переход от неудачного
компактного `execv` к прежнему внутрипроцессному reaper.

## Риски и ограничения

- Исходный объёмный `argv` кратковременно существует до self-`exec`; доработка
  устраняет его из steady state, но не создаёт отдельный конфиденциальный канал
  передачи параметров запуска.
- Если self-`exec` недоступен, fallback сохраняет корректность процесса, но
  исходная длинная командная строка остаётся видимой для этого запуска.
- Внутренний режим reaper является Linux-only частью helper и не расширяет
  пользовательский CLI Codex.
