# Токены и кредитная стоимость вызовов модели в TUI

## Обзор

Эта карточка фиксирует fork-доработку Hermione для показа статистики токенов и
расчётной кредитной стоимости рядом с уже существующими разделителями истории
TUI и терминальными событиями агентов. Первый обычный разделитель показывает
только накопление текущего отображаемого потока с начала пользовательского
хода; последующие также показывают в скобках дельту завершённых вызовов после
предыдущего разделителя. События
`Completed`, `Errored` и `Interrupted` сразу показывают накопление
соответствующего агента в текущем корневом ходе. При участии агентов перед
завершающим разделителем выводится итог основной модели, агентов и всей работы;
без агентов сокращённый `Total` входит в сам разделитель после `Worked for ...`.
Счётчики группируются по фактически использованной модели, сбрасываются на
границе следующего пользовательского хода и не накапливаются за всю историю
потока или сессии. Если в `config.toml` задан `credit_rates_path`, каждая
модельная запись также показывает стоимость по внешней таблице, а `Total` для
нескольких моделей — их общую кредитную сумму. Для каждого сохранённого
`TokenUsageRecord` JSONL также фиксируются фактическая модель и точная
историческая стоимость вызова в пикокредитах.

## Зачем это нужно

Responses API уже возвращал `usage` завершённого ответа, включая входные,
кэшированные входные, выходные и reasoning-токены. До этой доработки TUI
игнорировал `rawResponse/completed`, а само уведомление не содержало модель
ответа. `SubAgentActivityItem` также не нёс статистику токенов: фактический
терминальный путь публиковал структурированное событие только для успешного
`Completed`, а `interrupt_agent` публиковал `Interrupted` сразу после отправки
запроса на прерывание, ещё до фактического завершения дочернего хода.
Пользователь видел границы отдельных рабочих фаз, исходы агентов и общую
длительность хода, но не видел, сколько токенов потребовала каждая фаза и какие
модели участвовали.

Нужна локальная для TUI форма наблюдаемости:

- внутри первого обычного разделителя — накопительный итог отображаемого потока
  с начала текущего пользовательского хода; внутри последующих — тот же итог и
  дельта после предыдущего разделителя;
- после каждого `Completed`, `Errored` или `Interrupted` агента — его
  накопленные токены в пределах текущего корневого хода;
- перед завершающим `Worked for ...` — раздельные суммы основной модели,
  агентов и всей работы корневого хода, если участвовали агенты; без агентов —
  сокращённый `Total` в строке самого разделителя;
- отдельно по каждой модели, если в одном ходе модель менялась или сервер
  выполнил запрос другой моделью;
- с расчётной стоимостью каждой модельной записи и единым кредитным итогом там,
  где токены разных моделей намеренно остаются раздельными;
- с сохранением итоговой модели и точной исторической стоимости каждого
  `TokenUsageRecord` в JSONL;
- без ложного нуля, когда upstream не прислал `usage`.

Кредитная стоимость является локальной оценкой по выбранному пользователем
файлу тарифов, а не подтверждением фактического списания с баланса. Доработка не
вводит денежный биллинг или пожизненный счётчик потока.

  итоговых UI-строк в JSONL;
- сложение токеновых счётчиков разных моделей в одно число.

## Итоговый контракт

### Формат одной модельной записи

В терминальной строке агента и итоговом отчёте одна модель отображается так:

```text
Tokens: [gpt-5.6-sol] 1.89Ƶ, 1,841 in, 153,856 cached, 244 / 330 out
```

Несколько моделей остаются в одной логической строке и разделяются точкой с
запятой:

```text
Tokens: [gpt-5.6-sol] 6.6Ƶ, 2,230 in, 137,600 cached, 4,865 / 10,000 out; [gpt-5.6-luna] 0.19Ƶ, 1,120 in, 68,800 cached, 2,490 / 4,900 out
```

Первый обычный разделитель показывает только накопление модели с начала текущего
пользовательского хода, поскольку предыдущей границы для дельты ещё нет:

```text
─ Tokens: [gpt-5.6-sol] 1.12Ƶ, 585 in, 50,688 cached, 161 / 1,113 out ─────────
```

Начиная со второго фактически добавленного разделителя, каждая величина также
показывает в скобках дельту после предыдущей границы:

```text
─ Tokens: [gpt-5.6-sol] 3.85Ƶ (+1.24Ƶ), 678 (+150) in, 370,304 (+120,000) cached, 141 (+25) / 161 (+40) out ─────────
```

В накопительной части перечисляются все модели отображаемого потока,
наблюдённые с начала хода. На первом разделителе дельты отсутствуют для всех
моделей. На последующих разделителях, если модель не участвовала в последнем
интервале, её дельта равна `0`; новые модели получают накопление, равное первой
дельте. При нескольких моделях записи по-прежнему разделяются точкой с запятой и
сортируются по старшинству модели.

### Терминальное событие агента

После фактического терминального исхода агента соответствующая ячейка события
сразу показывает одну строку `Tokens:`:

```text
• Completed `/root/worker`
  └ Tokens: [gpt-5.6-luna] 0.27Ƶ, 1,760 in, 92,800 cached, 3,690 / 7,000 out

• Errored `/root/reviewer`
  └ Tokens: [gpt-5.6-terra] 1.09Ƶ+, 920 in, 40,000 cached, 1,700 / 2,800 out, partial

• Interrupted `/root/scout`
  └ Tokens: [gpt-5.5] ?Ƶ, unavailable
```

Строка показывает накопление только самого `agent_thread_id` в пределах
текущего `root_turn_id`, а не дельту последнего дочернего хода. Если того же
агента повторно запустили в том же корневом ходе, новая терминальная ячейка
показывает обновлённое накопление одной строкой без отдельного `Agent total`:

```text
• Completed `/root/worker`
  └ Tokens: [gpt-5.6-luna] 0.27Ƶ, 1,760 in, 92,800 cached, 3,690 / 7,000 out
```

При запуске того же агента из нового корневого хода используется новый
аккумулятор, поэтому показываются только токены нового `root_turn_id`.

`Completed`, `Errored` и `Interrupted` являются единственными терминальными
событиями `SubAgentActivity` этого контракта. `Interrupted` создаётся после фактического
`TurnAborted`, а не после успешной отправки запроса на прерывание. Для
`Errored` и `Interrupted` выводятся все уже наблюдённые счётчики, но
незавершённый ответ не считается нулевым и делает снимок неполным. Если ни один
счётчик получить не удалось, при включённом расчёте кредитов строка остаётся
видимой как `Tokens: [model] ?Ƶ, unavailable`, а при выключенном — как
`Tokens: [model] unavailable`. Когда даже модель неизвестна, используется
`Tokens: unavailable`.

### Итог корневого хода

Если в корневом ходе участвовал хотя бы один агент, сводка токенов располагается
отдельным блоком непосредственно перед завершающим разделителем
`Worked for ...` и содержит три строки:

```text
  Turn:   [gpt-5.6-sol] 6.27Ƶ, 3,450 in, 463,872 cached, 782 / 2,573 out
  Agents: [gpt-5.6-luna] 0.32Ƶ, 44,161 in, 156,672 cached, 408 / 546 out
  Total:  6.59Ƶ; [gpt-5.6-sol] 6.27Ƶ, 3,450 in, 463,872 cached, 782 / 2,573 out; [gpt-5.6-luna] 0.32Ƶ, 44,161 in, 156,672 cached, 408 / 546 out
─ Worked for 1m 15s ─────────────────────────────────────────────────
```

`Turn` содержит только вызовы основной модели в текущем корневом ходе.
`Agents` складывает прямые вызовы всех дочерних и вложенных агентов внутри
каждой модели. `Total` складывает `Turn` и `Agents` также только внутри
совпадающего slug модели. Токены разных моделей никогда не складываются в одно
число. Кредитная стоимость имеет общую единицу: если `Total` содержит несколько
моделей и стоимость каждой из них известна, перед модельными записями выводится
их общая сумма и точка с запятой. В `Turn`, `Agents`, обычном разделителе и
терминальном событии агента отдельная межмодельная сумма не добавляется.

Если агентов в корневом ходе не было, строки `Turn` и `Agents` отсутствуют, а
`Total` переносится в строку завершающего разделителя после `Worked for ...` и
отделяется тем же символом `•`, который уже разделяет метки этого компонента:

```text
─ Worked for 7m 57s • Total: [gpt-5.6-sol] 6.6Ƶ, 2,230 in, 137,600 cached, 4,865 / 10,000 out ─────────────────────
```

`Total` присутствует в финальном представлении всегда. Если существующее
условие скрывает короткую метку `Worked for ...`, сокращённый `Total` всё равно
остаётся внутри разделителя; существующие runtime-метрики располагаются после
него и также отделяются символом `•`. При одной модели её кредитная
стоимость остаётся только внутри модельной записи: отдельная общая сумма перед
ней не повторяется. Если итог не содержит ни одного доступного счётчика, он
отображается как `Total: [model] ?Ƶ, unavailable` либо `Total: unavailable`,
когда модель неизвестна. В трёхстрочной форме `Turn` и `Agents` также не
исчезают из-за неизвестного `usage`: отсутствующие данные обозначаются как
`unavailable`.

Участие агента определяется реестром запусков текущего `root_turn_id`, а не
наличием положительного счётчика. Поэтому запущенный агент с неизвестным
`usage` всё равно включает трёхстрочную форму и состояние `unavailable` либо
`partial`. При участии агентов существующие runtime-метрики сохраняют своё
место в строке завершающего разделителя отдельно от трёхстрочного отчёта.

Токены форматируются с ASCII-запятой как разделителем тысяч. Имя модели
показывается точным slug в квадратных скобках, без замены на маркетинговое
отображаемое имя. Кредитная стоимость располагается сразу после модели и перед
токенами. Единица записывается постфиксно знаком `Ƶ` (`U+01B5`, LATIN CAPITAL
LETTER Z WITH STROKE): `6.27Ƶ`.

### Смысл полей

Для каждого завершённого ответа:

```text
in                    = max(input_tokens - cached_input_tokens, 0)
cached                = max(cached_input_tokens, 0)
reasoning             = max(reasoning_output_tokens, 0)
total_out             = max(output_tokens, 0)
out_without_reasoning = max(total_out - reasoning, 0)
```

Первое число перед косой чертой — выход без reasoning-токенов, второе — полный
выход, уже включающий reasoning. Полный выход нельзя складывать с первым числом.
Поля `total_tokens`, `reasoning_output_tokens` и `cache_write_input_tokens`
отдельно не выводятся. Запись в кэш остаётся внутри `in`, потому что из
`input_tokens` вычитается только `cached_input_tokens`.

Полный выход после косой черты показывается всегда, в том числе как `/ 0 out`.
Начиная со второго обычного разделителя каждая накопительная величина
сопровождается дельтой в скобках: `141 (+25) / 161 (+40) out`.

При включённом расчёте стоимость одной завершённой модельной записи равна:

```text
credits = (in * input_rate + cached * cached_input_rate + total_out * output_rate) / 1,000,000
```

Reasoning-токены отдельно не тарифицируются, поскольку уже входят в `total_out`.
`cache_write_input_tokens` остаются внутри `in` и получают обычный входной
тариф. Стоимости ответов одной модели складываются с полной внутренней
точностью. Стоимости разных моделей также можно складывать, поскольку все они
выражены в кредитах; токеновые счётчики при этом остаются раздельными.

Для отображения стоимость округляется до ближайшей сотой кредита, а конечные
нули удаляются: `123Ƶ`, `6.5Ƶ`, `6.27Ƶ`. Положительное значение меньше сотой
имеет вид `<0.01Ƶ`. Неполная модельная запись показывает известную нижнюю
границу с суффиксом `+`, например `6.27Ƶ+`. Неизвестная стоимость имеет вид
`?Ƶ`. Общая сумма нескольких моделей вычисляется из неокруглённых модельных
стоимостей и округляется только после сложения. Если хотя бы одна стоимость
неизвестна, общий кредитный итог имеет вид `?Ƶ`; если все стоимости известны,
но хотя бы одна неполна, общий итог получает суффикс `+`.

### Тарифная таблица и конфигурация

Расчёт кредитов включается только явным параметром `credit_rates_path` в
`config.toml`. Встроенного пути и встроенной таблицы нет. В основном
`~/.codex/config.toml` для текущей установки используется:

```toml
credit_rates_path = "codex-credits.json"
```

Если параметр отсутствует, Codex не ищет тарифный файл и сохраняет прежний
формат без кредитной стоимости. Поле имеет тип `Option<AbsolutePathBuf>` и
использует тот же механизм разрешения путей, что `model_instructions_files` и
`developer_instructions_files`: относительное значение разрешается от каталога
того конфигурационного слоя, в котором оно задано. Поэтому приведённая строка в
`~/.codex/config.toml` указывает на `~/.codex/codex-credits.json`; в другом
конфигурационном слое базовым будет каталог файла этого слоя. Codex открывает
выбранный файл только для чтения и не создаёт, не обновляет и не перезаписывает
его.

Формат файла:

```json
{
  "schema_version": 1,
  "unit": "credits_per_million_tokens",
  "source": "https://learn.chatgpt.com/docs/pricing#__codexlocalizedvalueprops__codextranslations-u0141-token-rates",
  "models": {
    "gpt-5.6-sol": {
      "input": 100,
      "cached_input": 10,
      "output": 500
    }
  }
}
```

Ключи `models` являются точными фактическими slug. Неявное сопоставление по
префиксу, маркетинговому имени или ближайшей известной модели запрещено. Если
slug отсутствует в таблице, токены модели остаются видимыми, а стоимость
показывается как `?Ƶ`.

Числовые значения задают неотрицательные кредиты за миллион соответствующих
токенов в обычной десятичной записи максимум с шестью знаками после точки;
экспоненциальная запись не принимается. Для
первоначального файла используются следующие строки опубликованной таблицы:

| Slug модели | `input` | `cached_input` | `output` |
| --- | ---: | ---: | ---: |
| `gpt-6-astra` | 250 | 25 | 1250 |
| `gpt-5.6-sol` | 100 | 10 | 500 |
| `gpt-5.6-terra` | 50 | 5 | 300 |
| `gpt-5.6-luna` | 5 | 0.5 | 30 |
| `gpt-5.5` | 125 | 12.5 | 750 |
| `gpt-5.4` | 62.5 | 6.25 | 375 |
| `gpt-5.4-mini` | 18.75 | 1.875 | 113 |

Файл является единственным источником тарифов. Режим обработки, множители,
даты и промо-условия не изменяют загруженные значения. Ошибка чтения,
неподдерживаемая `schema_version`, неизвестная `unit`, некорректное число или
неполная запись модели не должны ломать токеновую сводку: стоимость затронутой
модели считается неизвестной, а пользователю показывается одна диагностическая
ошибка загрузки таблицы без повторения на каждом разделителе.

Сложение по модели должно быть насыщающим, чтобы повреждённое или чрезмерное
значение одного ответа не переполнило агрегат.

### Историческая стоимость в JSONL

Каждый новый `TokenUsageRecord` сохраняет два добавочных поля:

```json
{
  "model": "gpt-5.6-sol",
  "credit_cost_picocredits": "1121880000000"
}
```

`model` содержит итоговый slug, выбранный для того же завершённого ответа по
описанному ниже правилу фактической и резервной модели.
`credit_cost_picocredits` содержит стоимость именно этого ответа, рассчитанную
по эффективной таблице тарифов в момент его завершения. Значение записывается
десятичной строкой точного неотрицательного `u128`: один кредит равен
`1,000,000,000,000` пикокредитов. Округлённая экранная форма вроде `1.12Ƶ` в
JSONL не сохраняется.

Если тариф для модели или вся таблица недоступны, стоимость сохраняется как
`null`, а не как ноль. При resume сохранённая стоимость считается исторической
и не пересчитывается по текущему `codex-credits.json`. Итоги turn получают
точным сложением стоимостей его ответов и округляются только для отображения;
неизвестная стоимость любого ответа делает итог неизвестным.

Оба поля должны быть добавочными и необязательными при чтении: старая запись без
них означает неизвестные модель и историческую стоимость. Таблица тарифов, её
хеш и готовые снимки обычных разделителей, терминальных событий агентов и
финального `Total` в JSONL не добавляются.

### Области накопления

Доработка использует две связанные, но независимые области:

- TUI-аккумулятор хранит `since_turn_start` для накопления текущего
  отображаемого потока с начала пользовательского хода и `since_separator` для
  дельты после последнего фактически добавленного разделителя;
- общий реестр корневого хода хранит модельные записи по ключу
  `(root_turn_id, thread_id)` и отдельно отмечает основной поток и каждого
  агента.

Обе области продолжают хранить токены по моделям. Для живого отображения
кредитная стоимость является производной от замороженной модельной записи и
загруженного по `credit_rates_path` тарифа. Сохранённая стоимость ответа лишь
фиксирует результат этого расчёта и не образует третьего накопителя вызовов
модели.

В реестре ответ дедуплицируется по паре `(thread_id, response_id)`. Один и тот
же `response_id` в разных потоках не считается дублем. Агрегат агента содержит
только прямые вызовы модели этого `agent_thread_id`; вызовы его потомков имеют
собственные записи. В строках `Agents` и `Total` все ненулевые уровни дерева
сворачиваются напрямую по модели ровно один раз, поэтому вложенность не создаёт
двойного учёта.

Логическая форма ограниченного состояния:

```text
RootTurnUsageLedger[root_turn_id]
  root_thread_id
  turn_by_model
  agents[agent_thread_id]
    agent_path
    runs[agent_turn_id]
      terminal_state
      incomplete
    by_model
  seen_responses[(thread_id, response_id)]
  root_snapshot_emitted
```

`runs` нужен для различения повторных запусков, фактических терминальных исходов
и ещё работающих агентов. Он не задаёт окно отображаемых токенов: поле
`by_model` остаётся накопительным для пары `(root_turn_id, agent_thread_id)`.
Это позволяет обновлять одну строку `Tokens:` после каждого запуска агента, не
складывая повторно уже показанный снимок.

Успешный dispatch и начало дочернего хода выполняются конкурентно: дочерний ход
может начать модельный вызов или даже завершиться до того, как инициатор
зарегистрирует возвращённый запуск. Реестр должен согласовать такой уже
наблюдённый запуск с запоздавшей регистрацией, а не открыть второй pending-run и
не показать завершённого агента как работающего. Пока зарегистрированный агент
действительно остаётся нетерминальным, его модельная запись в замороженном итоге
помечается `partial` даже между двумя вызовами модели.

Последовательность переходов:

```text
старт корневого хода
  -> открыть область root_turn_id
  -> зарегистрировать основной thread_id

spawn_agent или followup_task
  -> зарегистрировать agent_thread_id в текущем root_turn_id
  -> отметить фактически запущенный дочерний ход как работающий

rawResponse/completed любого связанного потока
  -> дедуплицировать по (thread_id, response_id)
  -> добавить usage в запись точной модели этого потока
  -> для отображаемого потока также добавить usage в since_turn_start
     и since_separator

обычный разделитель
  -> создать неизменяемую пару снимков since_turn_start и since_separator
  -> добавить HistoryCell
  -> на первой границе показать только since_turn_start
  -> на последующих границах также показать since_separator как дельту
  -> очистить только since_separator

фактический Completed, Errored или Interrupted агента
  -> закрыть соответствующий дочерний ход
  -> создать накопительный снимок (root_turn_id, agent_thread_id)
  -> добавить терминальную ячейку события с одной строкой Tokens

завершение корневого хода
  -> создать неизменяемые снимки Turn, Agents и Total
  -> при участии агентов добавить токеновый блок перед FinalMessageSeparator
  -> без агентов добавить сокращённый Total в метки FinalMessageSeparator
  -> заморозить уже добавленную историю
```

`followup_task` создаёт новый дочерний ход, но не новый пользовательский
корневой ход. Если он наследует тот же `root_turn_id`, новая терминальная
ячейка показывает увеличенное накопление агента. Если вызов сделан из нового
корневого хода, тот же `agent_thread_id` получает отдельную запись с нулевой
начальной суммой. `send_message`, переданное работающему агенту, не открывает
самостоятельное окно: последующие ответы относятся к тому дочернему ходу,
который фактически обработал сообщение.

Один `agent_turn_id` может перейти в терминальное состояние только один раз.
Повторная доставка того же терминального события не добавляет вторую ячейку и
не меняет накопление; новый `followup_task` отличается новым `agent_turn_id`,
даже если `agent_thread_id` остался прежним.

Обычный разделитель показывает накопление завершённых вызовов модели
отображаемого потока с начала пользовательского хода. На первой границе дельта
не существует и не выводится; последующие границы показывают рядом дельту
предыдущего визуального блока. Асинхронные ответы других агентов не
подмешиваются ни в накопление, ни в дельту обычного разделителя: они
показываются в терминальных ячейках событий и в итоговом блоке корневого хода.
Несколько циклов с одними лишь вызовами инструментов или несколько ответов
модели без промежуточного разделителя накапливаются в одной дельте. Сам вызов
инструмента токены не потребляет; его результат влияет на вход следующего
вызова модели и отражается в `usage` следующего ответа.

Итог `Total` намеренно повторно включает `usage`, уже показанный в обычных
накоплениях и дельтах, а также в терминальных строках агентов: это сумма всего
корневого хода, а не очередная дельта. Ни один счётчик не наследуется следующим
`root_turn_id`, потоком или сессией. Межмодельный кредитный итог повторяет
стоимость тех же записей и не является дополнительным списанием.

Статистика токенов не меняет существующее условие появления разделителя. Если
TUI не создавал бы разделитель без этой доработки, наличие `usage` само по себе
его не создаёт. Даже если короткий ход не показывает `Worked for ...`,
добавленный в конце хода разделитель использует снимок общего реестра, а
обычный — пару снимков `since_turn_start` и `since_separator`; смысл не
выводится из видимой метки времени.

### Группировка и порядок моделей

Статистика `usage` группируется по точному slug итоговой модели. Повторные ответы одной
модели суммируются, разные slug не склеиваются.

Порядок не зависит от момента первого появления модели:

1. Распознанные `gpt-<version>` сортируются по числовым компонентам версии по
   убыванию: `gpt-6` старше `gpt-5.6-*`, а `gpt-5.6-*` старше `gpt-5.5`.
2. Для одинаковой версии известные суффиксы уровня идут в порядке
   `sol > terra > luna`.
3. Остальные суффиксы той же версии идут после известных уровней и получают
   стабильный лексикографический порядок по полному slug.
4. Нераспознанные модели идут после распознанных GPT-моделей и также сортируются
   лексикографически. Порядок поступления не используется для разрешения
   равенства.

Например:

```text
gpt-6 > gpt-5.6-sol > gpt-5.6-terra > gpt-5.6-luna > gpt-5.5
```

### Источник модели

Модель должна закрепляться за каждым ответом до отправки
`ResponseEvent::Completed`:

1. В начале запроса к модели используется разрешённый запрошенный slug из
   `StepContext`.
2. Если поток сообщает `ResponseEvent::ServerModel`, его значение заменяет
   резерв для этого ответа.
3. `rawResponse/completed` всегда несёт выбранное поле `model`, даже если `usage`
   отсутствует.

TUI не должен выводить модель из текущего состояния выбора: разрешённая модель
может измениться между ответами модели, а сервер может выполнить запрос
другой моделью. Фактическая модель уже читается из заголовка `openai-model`;
если заголовок не пришёл, резерв сохраняет честную известную модель запроса.

### Отсутствующий usage

Завершённый ответ с `usage: null` нельзя учитывать как нулевой. Снимок хранит
для каждой модели число ответов без `usage` отдельно от агрегированных чисел:

- если часть ответов модели имеет `usage`, а часть не имеет, её обычная запись
  получает суффикс `, partial`;
- если `usage` не пришёл ни для одного ответа модели, её запись имеет вид
  `[gpt-5.6-sol] ?Ƶ, unavailable` при включённом расчёте кредитов и
  `[gpt-5.6-sol] unavailable` при выключенном;
- если в интервале обычного разделителя не было ни одного завершённого ответа,
  метка `Tokens:` не добавляется;
- терминальная ячейка события агента не исчезает при отсутствии счётчиков и
  использует те же формы; при неизвестной модели она показывает
  `Tokens: unavailable`.

Например:

```text
Tokens: [gpt-5.6-sol] 6.6Ƶ+, 2,230 in, 137,600 cached, 4,865 / 10,000 out, partial; [gpt-5.6-luna] ?Ƶ, unavailable
```

Накопительная часть обычного снимка сохраняет неполноту модели с начала хода, а
дельта — только для своего интервала. Если интервал содержит и известные
счётчики, и завершение без `usage`, в скобках показывается известная нижняя
граница, а суффикс `, partial` относится ко всей модельной записи. Если у модели
интервала нет ни одного известного `usage`, но накопительный счётчик уже
известен, значения дельты показываются как `(+?)`, а стоимость — как `(+?Ƶ)`.
Если в дельте не было ответа ранее наблюдённой модели, для неё показываются
нулевые дельты. При полностью неизвестном накопительном счётчике запись
сохраняет форму `unavailable`, а кредитная часть при включённых тарифах всё
равно различает неизвестную дельту и нулевую дельту.

Снимок корневого хода сохраняет неполноту конкретной модели, если `usage`
отсутствовал хотя бы у одного её завершённого ответа. `Errored` или
`Interrupted` с незавершённым ответом модели также помечает накопление агента неполным:
известные предыдущие ответы остаются видимыми, но расход незавершённого ответа
не подменяется нулём. Неполнота `Agents` переносится в ту же модель строки
`Total`. Повторный успешный запуск того же агента в этом `root_turn_id` не
стирает неполноту предыдущего запуска.

### Область `thread` и `turn`

Пользовательской границей накопления является `root_turn_id`. Внутренний
дочерний `turn_id` определяет один запуск агента, но не сбрасывает его
накопление, если `root_turn_id` остался прежним. Позднее уведомление относится к
тому корневому ходу, с которым оно было создано, а не к ходу, активному в TUI в
момент доставки. Дубликат пары `(thread_id, response_id)` не учитывается
повторно.

В обе локальные части обычного разделителя входят только
`rawResponse/completed`, доставленные отображаемому `ChatWidget` и совпадающие
с его активными `thread_id` и `turn_id`. Общий реестр независимо принимает
ответы всех потоков, связанных с `root_turn_id`, чтобы итог не зависел от того,
какой агент сейчас открыт пользователем.

Если корневой ход завершается при ещё работающих агентах, финальный блок
замораживает все уже известные значения, помечает `Agents` и `Total` как
неполные и сообщает число работающих агентов. Поздний `Completed`, `Errored`
или `Interrupted` добавляет свою терминальную ячейку с обновлённым накоплением,
но не переписывает старый финальный блок. Реестр такого корневого хода живёт до
последнего терминального события либо завершения сессии, после чего очищается.

`HistoryCell` получает уже замороженный снимок. Изменение размера, повторная
отрисовка, переключение режима transcript и открытие полного transcript не
изменяют счётчики и не сдвигают границу интервала. Полная метка остаётся
доступна через `raw_lines`; на экране действует существующее ограничение
разделителя по ширине терминала.

## Архитектурное решение

### Почему нужно событие для каждого ответа

Существующий `ThreadTokenUsageUpdatedNotification` сообщает накопительный
расход потока и не закрепляет его за моделью конкретного ответа. Вычитание двух
таких сумм в TUI было бы хрупким: оно связывало бы UI-дельту с порядком
асинхронных накопительных обновлений, затрудняло смену модели и могло бы давать
отрицательные значения после сброса или воспроизведения.

Поэтому единицей учёта остаётся уже существующий `rawResponse/completed`. В него
добавляется итоговая модель. TUI использует событие для локального накопления и
дельты обычного разделителя, а общий реестр дерева агентов складывает записи
всех потоков по `root_turn_id`.

### Почему фактическая модель фиксируется в core

`ResponseEvent::ServerModel` возникает в том же цикле обработки ответа модели, где
затем приходит `ResponseEvent::Completed`. Только этот уровень однозначно знает
пару «сообщённая сервером модель + `usage` данного ответа». Передавать наружу
только предупреждение о перенаправлении недостаточно: оно может быть подавлено
после первого раза и не является структурированным событием учёта.

Если сообщённая сервером модель не пришла, разрешённая модель из того же
`StepContext` является лучшим доступным резервом. Текущую модель TUI использовать
нельзя, поскольку следующий запрос к модели уже может иметь другой
`StepContext`.

### Почему общий реестр находится выше TUI

Терминальное событие агента может прийти в поток непосредственного инициатора,
а не обязательно в корневой `ChatWidget`. Вложенные и повторно запущенные
агенты также завершаются независимо от активного представления. Поэтому TUI не
должен восстанавливать итог обходом видимых ячеек истории или вычитанием
накопительных счётчиков потоков. Общий для дерева агентов реестр записывает
каждый ответ модели один раз и передаёт в UI уже замороженные снимки агента и
корневого хода.

### Почему токены остаются модельными, а кредиты складываются

У разных моделей различаются токенизация, контекст и стоимость; арифметическая
сумма их токенов вводила бы в заблуждение. Поэтому все три строки хранят карту
`model -> usage`. `Agents` сворачивает прямые записи агентов только внутри
одного slug, а `Total` складывает `Turn` и `Agents` только для совпадающего
slug. Общего числа токенов поверх разных моделей не существует. Кредиты уже
нормализуют расход через модельные тарифы, поэтому стоимости разных slug можно
сложить в единый итог. Этот итог дополняет модельные записи, но не заменяет их.

### Почему тарифы находятся во внешнем JSON

Тарифы меняются независимо от жизненного цикла бинарника и являются локально
выбранными данными пользователя. Поэтому бинарник не содержит резервных цен и
не обращается к сети за таблицей. Явный `credit_rates_path` отделяет включение
расчёта от места хранения файла, а отсутствие параметра полностью сохраняет
прежнее отображение токенов.

Файл `~/.codex/codex-credits.json` создаётся один раз как отдельное действие
этой доработки. Он не является артефактом `fork install`, не принадлежит
автоматическому обновлению и после создания остаётся пользовательским файлом.

### Почему терминальный снимок создаётся после исхода агента

Успешная отправка `Op::Interrupt` ещё не означает, что дочерний ход остановился:
между запросом и фактическим `TurnAborted` может появиться завершающий ответ или
новая статистика. Поэтому `interrupt_agent` не является границей учёта.
Терминальную ячейку `SubAgentActivity` для `Completed`, `Errored` или `Interrupted`
создаёт единый путь обработки фактического исхода, после записи всех
предшествующих `rawResponse/completed`.

### Почему снимок принадлежит `HistoryCell`

Граница интервала или терминального состояния возникает в момент добавления
ячейки, а не во время её отрисовки. Поэтому ячейка должна владеть неизменяемой
парой накопительного и интервального снимков либо готовым терминальным снимком.
Если отрисовщик будет читать живой аккумулятор, изменение размера, повторная
отрисовка или новый запуск того же агента изменит уже показанное значение.

### Совместимость app-server

Поля `model`, снимок терминального агента и итог корневого хода являются
добавочными полями v2 API. Они должны присутствовать в новых уведомлениях, быть
отражены в сгенерированных schema/TypeScript и документированы. Добавление
`Errored` расширяет передаваемый enum `SubAgentActivityKind`; совместимость клиентов с
неизвестным вариантом нужно проверить отдельно. Смысл существующих полей
`usage` не меняется.

`rawResponse/completed` остаётся opt-in уведомлением. TUI явно включает его при
`thread/start`, `thread/resume` и `thread/fork`; app-server должен сохранить opt-in
как для холодного возобновления, так и при повторном присоединении к уже
загруженному потоку. Остальные клиенты по умолчанию продолжают работать без
сырых событий.

Сохранённый `TokenUsageRecord` содержит `thread_id`, `turn_id`, `root_turn_id`,
`response_id`, токены ответа, итоговую модель и точную историческую стоимость
ответа. Модель и стоимость появляются только в новых записях; их отсутствие в
старом JSONL означает неизвестные значения и не является ошибкой чтения.

Историческая стоимость принадлежит записи, а не текущей таблице тарифов:
изменение `codex-credits.json` после завершения ответа не должно менять её при
resume. Карточка не сохраняет таблицу, её хеш или готовые UI-снимки и не
дополняет задним числом старые разделители и ячейки событий.

## Порядок повторения при переносе

1. Проверить текущий upstream-отрисовщик обычного и завершающего разделителей,
   терминальные ячейки событий агентов и все пути `TurnComplete`/
   `TurnAborted`.
2. Проверить, продолжает ли поток Responses отдавать фактическую модель через
   `openai-model`, и найти `ResponseEvent::Completed` с `usage` отдельного
   ответа.
3. Закрепить итоговую модель за `ResponseEvent::Completed` в цикле обработки
   ответа: разрешённый запрошенный slug использовать как резерв, а сообщённую
   сервером модель — как приоритетное значение.
4. Добавить `credit_rates_path: Option<AbsolutePathBuf>` без значения по
   умолчанию, отразить его в config schema и передать TUI. Относительный путь
   должен разрешаться существующим механизмом от каталога содержащего его
   конфигурационного слоя. При отсутствии ключа не искать тарифный файл и
   сохранить прежний токеновый формат.
5. Загрузить и провалидировать внешний JSON только по явно заданному пути.
   Структурную ошибку таблицы отделять от ошибки отдельной модельной записи,
   чтобы токены всегда оставались видимыми, а известные корректные тарифы не
   терялись из-за одного повреждённого slug.
6. Ввести общие типы модельной записи, снимка агента и итогового снимка
   `Turn`/`Agents`/`Total`. Арифметика токеновых типов должна разрешать сложение
   только для одинакового slug модели. Тарифы нужно разбирать в точное
   десятичное представление без двоичного `float`, а промежуточную арифметику —
   защищать от переполнения.
7. Добавить общий реестр дерева агентов с ключами `root_turn_id`, `thread_id` и
   `(thread_id, response_id)`. Зарегистрировать основной поток, все успешные
   запуски агентов и новые дочерние ходы от `followup_task`.
8. Записывать каждый `rawResponse/completed` в общий реестр до публикации
   зависимого терминального события. Отдельно передавать событие отображаемому
   `ChatWidget` для накопления `since_turn_start` и дельты
   `since_separator`.
9. В сохраняемый `TokenUsageRecord` добавить необязательные при чтении поля
   `model` и `credit_cost_picocredits`. Для новой записи фиксировать итоговую
   модель и точную стоимость ответа по действующим в момент завершения тарифам;
   неизвестную стоимость сохранять как `null`, а после resume не пересчитывать.
10. Перенести `Interrupted` с момента отправки `Op::Interrupt` на фактический
   `TurnAborted` и публиковать из единого терминального пути `Completed`,
   `Errored` или `Interrupted` вместе с накопительным снимком агента.
11. Пронести поле `model` и готовые снимки через core-события, преобразование
    app-server и v2. Явно включить `experimentalRawEvents` во всех TUI-путях
    создания, возобновления и ответвления потока; обновить документацию API и
    сгенерированные артефакты.
12. При обычном разделителе замораживать `since_turn_start`, а после первой
    фактической границы также `since_separator`; очищать только
    `since_separator` и не подмешивать ответы других потоков. Новый
    пользовательский ход должен очищать обе области, признак предыдущей границы
    и набор дедупликации.
13. Для каждой модельной записи вычислять кредитную стоимость по точному slug и
    неокруглённым счётчикам. Округлять только форматируемое значение; общий
    кредитный итог нескольких моделей вычислять до округления модельных сумм.
14. Под терминальным событием агента рисовать одну строку `Tokens:`. Повторный
    запуск того же агента в одном `root_turn_id` должен показывать обновлённое
    накопление без отдельной дельты и без `Agent total`.
15. Перед завершающим разделителем рисовать `Turn`, `Agents` и `Total`, если
    участвовал агент. Без агентов переносить сокращённый `Total` внутрь строки
    разделителя после `Worked for ...`, используя существующий разделитель
    меток `•`. Не менять условие появления самого разделителя. Межмодельную
    кредитную сумму добавлять только в много-модельный `Total`.
16. Сначала закрепить арифметику токенов и кредитов, загрузку таблицы,
    отсутствие `credit_rates_path`, ошибки тарифов, округление,
    JSONL-совместимость, историческую стоимость, жизненный цикл, терминальные
    исходы и сортировку модульными и интеграционными тестами, затем добавить
    snapshot-тесты точного отображения и только после этого менять рабочую
    реализацию.
17. Проверить, что старые клиенты app-server корректно обрабатывают добавочные
    поля и расширенный enum, старые `TokenUsageRecord` читаются без новых полей,
    а TUI не восстанавливает новые сводки из старой сохранённой истории.
18. Заменить временное исключение `manual-required` исполняемой картой
    `fork-tests.v1` сразу после добавления тестов и до реализации рабочего кода.

## Риски и ограничения

- Статистика `usage` приходит только в `ResponseEvent::Completed`. Ответ,
  оборванный до этого события без счётчиков токенов, нельзя точно оценить по
  текущему событийному контракту; показанные числа покрывают только наблюдённые
  завершённые ответы.
- Без `experimentalRawEvents` TUI не получает `rawResponse/completed`: обычные
  разделители останутся без накопления и дельты даже при корректном учёте
  итогового снимка в core. Opt-in должен сохраняться во всех трёх
  lifecycle-путях, включая повторное присоединение к уже загруженному потоку.
- `usage: null` означает неизвестное значение, а не бесплатный ответ. Потеря
  признака `partial` создаст ложную точность.
- Если `credit_rates_path` отсутствует, кредитный расчёт полностью выключен:
  Codex не должен неявно искать `~/.codex/codex-credits.json` или любой другой
  файл.
- Недоступный либо структурно некорректный тарифный файл, неизвестная версия
  схемы и отсутствующий или повреждённый slug не должны скрывать токены. Цена
  затронутой модели становится `?Ƶ`, а ошибка загрузки сообщается один раз без
  повторения на каждом разделителе.
- Внешняя таблица может устареть. Codex намеренно не обновляет её, не применяет
  тарифные множители и промо-условия и не выдаёт вычисленную оценку за
  фактическое списание.
- Историческая стоимость в `TokenUsageRecord` остаётся неизменной после записи,
  даже если пользователь заменил таблицу тарифов. Resume не должен смешивать её
  с пересчитанными по новой таблице значениями.
- Отсутствующие `model` и `credit_cost_picocredits` в старом JSONL означают
  неизвестные значения. Десериализация не должна подменять их текущей моделью
  или нулевой стоимостью.
- Десятичные тарифы вроде `0.5` и `1.875` нельзя считать через двоичный `float`:
  итог должен быть детерминированным, защищённым от переполнения и округляться
  только после сложения точных значений.
- Заголовок сервера `openai-model` может отсутствовать. В этом случае метка
  отражает разрешённую запрошенную модель как явно определённый резерв, а не
  доказанную модель перенаправления на сервере.
- Один и тот же `response_id` может быть повторно доставлен при ошибке
  маршрутизации или воспроизведении. Без дедупликации по паре
  `(thread_id, response_id)` итог удвоится либо ответы разных потоков будут
  ошибочно склеены.
- Много моделей создают длинную однострочную метку. Экранный разделитель
  сохраняет существующую обрезку по ширине, поэтому старшие модели идут первыми;
  полная метка должна оставаться в `raw_lines`.
- `Total` повторяет токены из предыдущих накопительных и интервальных сводок и
  терминальных строк агентов. Это намеренно, но UI и тесты не должны давать
  оснований читать его как ещё одну дельту.
- Токены разных моделей нельзя складывать. Любой скрытый общий токеновый итог в
  типах, форматтере или тестовых ожиданиях нарушит пользовательский контракт;
  исключение относится только к нормализованной кредитной стоимости в строке
  `Total`.
- Символ `Ƶ` должен проходить snapshot-проверку как один элемент отображаемого
  текста; расчёт ширины и обрезка разделителя не должны разрывать стоимость и
  постфиксную единицу.
- Отправка запроса на прерывание и фактический `TurnAborted` разделены во
  времени. Если публиковать `Interrupted` из обоих мест, пользователь получит
  ранний снимок и дубликат терминальной ячейки.
- Возврат успешного `spawn_agent` или `followup_task` и фактическое начало
  дочернего хода могут прийти в реестр в обратном порядке. Запоздалая
  регистрация не должна повторно открыть уже завершённый запуск.
- Корневой ход может завершиться раньше агента. Финальный снимок в таком случае
  остаётся неполным и неизменяемым, а реестр нельзя очищать до позднего
  терминального события или завершения сессии.
- Поля уведомлений и новый вариант `SubAgentActivityKind` относятся к публичному API v2:
  schema, TypeScript, README и поведенческие тесты должны меняться вместе.
- Состояние реестра нельзя переносить между разными `root_turn_id` или
  возобновлёнными сессиями; иначе новый ход получит токены предыдущей работы.
