# Восстановление транспорта MCP stdio

## Обзор

Карточка владеет узкой fork-доработкой, которая восстанавливает упавшее
соединение MCP stdio без сохранения диагностики, перехвата stderr и изменений
контекста, видимого модели.

## Зачем это нужно

После смерти процесса MCP stdio сохранённый список инструментов может оставаться
доступным, хотя фактический транспорт уже закрыт. Следующий реальный вызов тогда
завершается `Transport closed` или ошибкой записи `BrokenPipe`.

Без автоматического восстановления пользователь получает ошибку и должен
вручную повторить действие либо перезапустить сессию. Требуемое поведение:

1. Обнаружить закрытый транспорт stdio или мёртвый дескриптор процесса.
2. Сериализовать восстановление, чтобы конкурентные вызовы не создавали несколько
   новых соединений.
3. Пересоздать транспорт из сохранённого `transport_recipe`.
4. Повторить инициализацию MCP с сохранённым `initialize_context`.
5. Заменить текущий `RunningService`.
6. Повторить исходную операцию ровно один раз.

Восстановление не должно создавать фоновый цикл перезапуска. Если процесс умер
в простое, новый запуск создаётся только при следующей реальной операции MCP.

## Итоговый контракт

### Область применения

Автоматическое восстановление после `TransportClosed` и `BrokenPipe`
применяется только к `TransportRecipe::Stdio`. Это одинаково относится к
legacy lifecycle и к явно включённому MCP `2026-07-28`: повторный запуск
использует сохранённый `McpProtocolMode`, а
`connect_pending_transport_with_initialize_retries` для stdio без повторов
делегирует в `connect_pending_transport`, который повторно выбирает
соответствующий `ClientLifecycleMode`. Повторы инициализации, предназначенные
только для HTTP, не распространяются на stdio. Для Streamable HTTP сохраняется
существующее отдельное восстановление после `SessionExpired404`.
Варианты `PendingTransport::StreamableHttpWithOAuth` и
`PendingTransport::StreamableHttpWithAccessTokenOnly` не получают stdio-дескриптор
и не входят в эту ветку восстановления.

Транспорт in-process не получает новое правило повтора.

### Признак мёртвого запуска

Каждый `StdioServerProcessHandle` содержит только атомарный признак смерти:

- получение из транспорта возвращает EOF — запуск помечается мёртвым;
- отправка в транспорт возвращает `io::ErrorKind::BrokenPipe` — запуск помечается
  мёртвым;
- явное завершение через дескриптор процесса также помечает запуск мёртвым;
- тестовый `MCP_TEST_EXIT_FILE` потребляется перед завершением процесса, поэтому
  восстановленный процесс не наследует уже сработавший маркер выхода;
- признак не содержит `launch_id`, stderr, временную метку или диагностические
  метаданные.

Признак `dead` независим от `terminated` и конкретного локального механизма
завершения дерева процессов, включая Windows-варианты `Job` и `Process`:
усиленная очистка процессов не заменяет сигнал для ленивого восстановления
транспорта.

Для локальных `LocalLegacy` и `LocalModern`, а также запускаемого через executor
stdio используется один `StdioServerTransport`, поэтому признак не требует
отдельной подсистемы журналирования процессов. Различие локальных transport
сохраняется только во внутреннем dispatch `send`/`receive`/`close`.

### Ленивое восстановление после смерти в простое

Перед каждой операцией MCP `RmcpClient` проверяет текущий дескриптор процесса
stdio. Если запуск мёртв:

1. Текущий `RunningService` фиксируется как сервис, на котором произошёл сбой.
2. Восстановление выполняется под `session_recovery_lock`.
3. Если другой конкурентный вызов уже заменил сервис, повторное подключение не
   выполняется.
4. Иначе создаётся новый транспорт, выполняется инициализация и заменяется
   сервис.
5. Операция выполняется на новом сервисе.

Все публичные операции, создающие запрос MCP через текущий `RmcpClient`, входят
в эту границу. Текущий метод `send_event_stream_request` также
вызывает `run_service_operation`, поэтому отправка `events/stream` не обходит
проверку мёртвого stdio-процесса и однократный повтор ошибки отправки.

Фоновая задача для периодического перезапуска, задержки повторов или проверки
работоспособности не создаётся.

### Граница startup и stable bindings

Recovery применяется только к уже успешно инициализированному `RmcpClient`.
Необязательный сервер, который не успел за общий startup grace и был исключён
из текущего stable `McpBinding`, не запускается и не восстанавливается этой
доработкой. Late startup и повторное формирование каталога остаются контрактом
connection manager.

Согласование состояния `pending` при startup и замена `trusted_access` после
первого `Failed` принадлежат `fork-mcp-startup-refresh-serialization` и не входят
в восстановление транспорта.

Если готовый сервер умер после захвата binding, подготовленный вызов продолжает
использовать тот же `Arc<RmcpClient>`. Recovery заменяет только внутренний
`RunningService`, не подменяет захваченный client и не меняет revision каталога.
Поэтому однократный повтор остаётся частью исходной operation и не превращается
в маршрутизацию вызова на поздно появившийся либо другой client.

### Восстановление после ошибки операции

Если операция завершилась `ServiceError::TransportClosed` либо
`ServiceError::TransportSend` с `io::ErrorKind::BrokenPipe`, `RmcpClient`
запускает то же сериализованное восстановление и повторяет исходную операцию
ровно один раз.

Повтор вызывается напрямую, а не через рекурсивную точку входа восстановления.
Поэтому повторный `TransportClosed` или `BrokenPipe` возвращается вызывающему
коду и не создаёт второй цикл восстановления.

### Конкурентные вызовы

`session_recovery_lock` сериализует замену транспорта. После захвата блокировки
восстановление через `Arc::ptr_eq` сравнивает текущий сервис с сервисом, на
котором произошёл сбой:

- если сервис уже заменён, новый запуск не создаётся;
- если сервис прежний, только текущее восстановление создаёт транспорт и
  выполняет инициализацию;
- каждая конкурентная операция может повторить только собственный исходный
  вызов.

### Ошибки восстановления

Ошибка создания транспорта или инициализации возвращается наружу. Старый
закрытый транспорт не считается восстановленным, а автоматический повтор без
успешной повторной инициализации не выполняется.

### Журналирование и поведение, видимое модели

Доработка не добавляет:

- `RolloutItem::McpDiagnostic`;
- `McpDiagnosticItem` или `McpDiagnosticEvent`;
- ограниченный хвост stderr;
- диагностический контекст с `thread_id`, `turn_id`, `call_id` или `launch_id`;
- события tracing для восстановления;
- строки SQLite;
- вывод инструмента, элемент истории или фрагмент контекста модели.

Существующее журналирование stderr процесса MCP из upstream остаётся без
изменений, но не расширяется и не используется механизмом восстановления.

## Архитектурное решение

### Почему восстановление живёт в `RmcpClient`

`RmcpClient` уже хранит все необходимые зависимости:

- `transport_recipe` для повторного создания транспорта;
- `initialize_context` для повторного рукопожатия;
- `session_recovery_lock` для устранения дубликатов конкурентного
  восстановления;
- замыкание операции в `run_service_operation` для однократного повтора.

Перенос восстановления в `codex-mcp` или `core` потребовал бы протаскивать
состояние транспорта через дополнительные слои и дублировал бы уже существующее
восстановление HTTP-сессии.

### Почему признак смерти принадлежит дескриптору транспорта

Место запуска процесса различается для локального и запускаемого через executor
stdio, но оба варианта сходятся в `StdioServerTransport`. Атомарный признак даёт
`RmcpClient` минимальный сигнал жизнеспособности без API конкретного типа
процесса, буфера stderr или сохраняемого идентификатора.

Признак служит ранним сигналом, а ошибка транспорта остаётся обязательным
резервным механизмом: процесс может быть ещё формально жив, но уже не принимать
запросы.

## Порядок повторения при переносе

1. Проверить текущую форму `RmcpClient`, `TransportRecipe`,
   `InitializeContext` и существующего восстановления HTTP-сессии.
2. Сохранить один заменяемый дескриптор процесса stdio на клиент, не меняя
   stable binding connection manager; вспомогательная функция извлечения
   дескриптора должна исчерпывающе возвращать `None` для всех вариантов
   `PendingTransport`, кроме `Stdio`.
3. Добавить минимальный признак смерти к дескриптору процесса и выставлять его
   при EOF, `BrokenPipe` и вызове `terminate`; оборачивать этим признаком все
   актуальные варианты `LocalLegacy`, `LocalModern` и executor transport.
4. Перед операцией выполнять ленивое восстановление мёртвого запуска.
5. Направить `TransportClosed` и stdio `BrokenPipe` в существующую
   границу сериализованной повторной инициализации, повторно используя
   сохранённые protocol mode и lifecycle, но не включая для stdio повторы
   инициализации, предназначенные только для HTTP.
6. Повтор исходной операции выполнять один раз без рекурсивного входа в
   восстановление.
7. При появлении новых публичных операций проверить, что они используют
   `run_service_operation`, а не получают `RunningService` напрямую.
8. Сохранить управляемый тестовый сервер и интеграционные сценарии, используя
   `MCP_TEST_EXIT_FILE` для завершения процесса в простое и не возвращая
   отдельный планировщик выхода для восстановления или проверки диагностических
   событий.
9. Проверить, что протокол, rollout, состояние, перехват stderr и данные,
   видимые модели, не изменились.

Target `mcp_2026_stdio` проверяет через публичный `RmcpClient`:

- два конкурентных сбоя одного `RunningService`, один новый запуск и независимый
  однократный повтор обеих операций;
- настоящий `TransportSend(BrokenPipe)` при закрытом stdin и удерживаемом stdout;
- ленивое восстановление перед отправкой нового `events/stream` после смерти
  stdio-процесса в простое;
- ошибку создания нового транспорта без повторного вызова исходной операции;
- ошибку повторной инициализации без замены старого закрытого сервиса;
- успешное восстановление следующим внешним вызовом после каждой из двух ошибок.

## Риски и ограничения

- Операции MCP, включая `tools/call`, считаются идемпотентными. Если сервер
  выполнил побочный эффект, но транспорт закрылся до доставки ответа, повтор
  способен выполнить побочный эффект ещё раз.
- Признак смерти доказывает закрытие транспорта, но не является полной проверкой
  работоспособности. Зависший живой процесс без EOF и без ошибки отправки этой
  доработкой не восстанавливается.
- Ошибка запуска нового процесса или инициализации возвращается пользователю;
  повторная попытка восстановления в рамках того же исходного вызова отсутствует.
  Следующий внешний вызов снова пытается восстановить сохранённый закрытый сервис.
- Восстановление не перечитывает изменённую конфигурацию MCP. Оно повторно
  использует сохранённый `transport_recipe` и выбранный protocol mode текущего
  клиента.
- Фоновый перезапуск намеренно отсутствует, поэтому умерший в простое сервер
  остаётся остановленным до следующей операции.
- Сервер, не вошедший в stable binding из-за startup grace или late startup, не
  получает recovery-вызов до появления в новом binding; эта карточка не меняет
  правила публикации каталога.
