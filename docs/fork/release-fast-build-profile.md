# Профиль `release-fast` и ревизия runtime-бинарников

## Обзор

Эта карточка фиксирует две связанные fork-доработки Codex:

- отдельный Cargo-профиль `release-fast` для быстрой оптимизированной сборки;
- сведения о ревизии сборки в исполняемых файлах `codex` и
  `codex-code-mode-host`.

Профиль наследует оптимизации upstream `release`, но сохраняет параллельность
финальных стадий. Оба бинарника используют `codex-build-info`, хранят ревизию в
конечном executable и показывают её отдельной строкой в `--version`.

## Зачем это нужно

Upstream-профиль `release` сохраняет таблицы строк для symbolication и ограничивает
параллельность финальной генерации кода. Для локальной разработки Hermione нужен
отдельный оптимизированный профиль, который быстрее собирается и сохраняет
таблицу символов для профилирования, но не меняет канонический профиль выпуска.

Одной SemVer-версии недостаточно, чтобы определить происхождение конкретного
бинарника: несколько сборок одного выпуска могут относиться к разным коммитам.
Кроме того, `codex` имеет fork-суффикс версии, а `codex-code-mode-host` наследует
workspace-версию без него. Отдельная строка ревизии связывает оба исполняемых
файла с исходным состоянием независимо от версии их пакетов.

## Итоговый контракт

### Профиль сборки

`codex-rs/Cargo.toml` содержит профиль:

```toml
[profile.release-fast]
inherits = "release"
codegen-units = 32
debug = "none"
```

Через наследование профиль получает текущие настройки оптимизации `release`, в
том числе `lto = "thin"` и `strip = false`. Он переопределяет только число
codegen units и объём отладочной информации. Канонический профиль `release`
остаётся неизменным.

Внутренняя цель `build-fast-release` в корневом `justfile` одной Cargo-сборкой
обрабатывает пакеты `codex-cli` и `codex-code-mode-host` с профилем
`release-fast`. Результатом становятся:

```text
codex-rs/target/release-fast/codex
codex-rs/target/release-fast/codex-code-mode-host
```

### Встроенная ревизия

Оба конечных бинарника вызывают `codex_build_info::initialize!()` до разбора
CLI-аргументов. Макрос раскрывает `option_env!("STABLE_GIT_COMMIT")` в crate
конкретного executable, кодирует значение в payload размером 40 байт и
инициализирует глобальный `BuildInfo`.

При отсутствии `STABLE_GIT_COMMIT` payload содержит `dev` с нулевым дополнением.
Непустое значение времени компиляции также дополняется нулями и не может
превышать 40 байт. Декодирование заканчивается на первом нулевом байте и требует
корректный UTF-8.

На ELF-целях payload размещается в отдельной загружаемой секции
`.hermione_revision`. Фиксированный размер позволяет обновлять существующую
секцию без повторной линковки executable. На остальных поддерживаемых целях
значение времени компиляции остаётся в используемом статическом объекте, но
отдельное имя ELF-секции не применяется.

`BuildInfo` сохраняет версию пакета и ревизию как независимые значения.
Корневые вызовы `codex --version` и `codex-code-mode-host --version` возвращают
ровно две строки:

```text
<command> <package-version>
revision <build-commit>
```

Для основного бинарника `<command>` равен `codex`, для host-бинарника —
`codex-code-mode-host`. Значение `<package-version>` берётся из Cargo-пакета
конкретного executable. Корневой `--help` и справка подкоманд строку ревизии не
показывают.

Bazel передаёт `STABLE_GIT_COMMIT` конечным штампуемым binary через `defs.bzl`.
Значение раскрывается в каждом executable отдельно, поэтому секция не зависит от
того, сохранил ли линкер неиспользуемый объект общей библиотеки.

## Архитектурное решение

`release-fast` остаётся отдельным профилем, наследующим upstream `release`.
Так fork меняет скорость локальной оптимизированной сборки, не переопределяя
параметры канонического выпуска. Общая цель сборки обрабатывает `codex` и
`codex-code-mode-host` как пару, чтобы оба конечных executable создавались с
одинаковым профилем.

Ревизия хранится в самих исполняемых файлах, а не вычисляется через Git во время
запуска. Макрос размещает статический payload в `main.rs` каждого binary и
инициализирует `BuildInfo` до того, как Clap может завершить процесс после
`--version`. Это не даёт секции исчезнуть вместе с неиспользованным объектом
библиотеки и не требует runtime-доступа к рабочей копии Git.

Фиксированный 40-байтный payload соответствует полному SHA-1 Git. Ревизия не
является частью SemVer: версия пакета определяет совместимость выпуска, а
`build_commit` — происхождение конкретного executable. Карточка
`hermione-version-metadata.md` отдельно владеет суффиксом `+hermione` и правилами
сравнения версий.

Изменения не затрагивают transport, протокол или поиск
`codex-code-mode-host`; для host меняются только сведения о сборке и вывод
корневого `--version`.

## Порядок повторения при переносе

### 1. Восстановить профиль и цель сборки

В `codex-rs/Cargo.toml` рядом с `[profile.release]` добавить
`[profile.release-fast]`, наследующий `release` и переопределяющий
`codegen-units = 32` и `debug = "none"`. Не копировать унаследованные значения
`lto` и `strip`: они должны следовать за актуальным upstream-профилем.

В корневом `justfile` сохранить цель `build-fast-release`, которая одной
Cargo-сборкой обрабатывает `codex-cli` и `codex-code-mode-host` с новым профилем.

### 2. Подключить `codex-build-info`

Добавить crate в workspace dependencies и зависимости `codex-cli` и
`codex-code-mode-host`. Обновить `Cargo.lock` и `MODULE.bazel.lock` штатными
генераторами репозитория.

В `codex-rs/build-info/src/lib.rs` сохранить 40-байтное кодирование revision
payload, нуль-терминированное декодирование и макрос `initialize!()`. На ELF
макрос должен создавать ровно одну используемую секцию `.hermione_revision` в
каждом конечном executable.

### 3. Подключить ревизию к CLI

В обоих `main.rs` вызвать `codex_build_info::initialize!()` до операции Clap,
которая обрабатывает `--version`. Версия команды должна состоять из версии
пакета и отдельной строки `revision <build-commit>`; справка не должна получать
эту строку.

Не переносить метку ревизии в общий статический объект библиотеки: секция должна
принадлежать каждому конечному executable и раскрываться с его окружением
времени компиляции.

### 4. Сохранить штампование Bazel

В `defs.bzl` передавать `STABLE_GIT_COMMIT` в `rustc_env` конечных
`rust_binary` и оставлять для них `stamp = 1`. Cargo-сборка без этой переменной
должна получать значение `dev`.

## Риски и ограничения

### Ограничения

- Канонический профиль `release` нельзя менять ради ускорения локальной сборки.
- `release-fast` должен наследовать `release` и переопределять только параметры,
  составляющие fork-дельту.
- Ревизия остаётся отдельной от SemVer и не заменяет суффикс `+hermione`.
- Макрос `initialize!()` должен вызываться в каждом конечном executable, а не в
  общей библиотеке.
- Размер payload фиксирован значением `BUILD_COMMIT_STAMP_LEN = 40`; более
  длинное значение времени компиляции недопустимо.
- Именованная секция `.hermione_revision` является ELF-специфичной. На других
  платформах доступно compile-time значение, но не этот binary layout.

### Риски

- Изменение настроек upstream `release` меняет и унаследованное поведение
  `release-fast`; после переноса нужно проверить итоговый профиль.
- Уменьшение `codegen-units` до значения канонического `release` лишит профиль
  ожидаемого выигрыша во времени сборки.
- Смена формата Git object ID на значение длиннее 40 байт потребует нового
  формата payload и совместимого декодирования.
- Если макрос будет перенесён из конечного binary в библиотеку, линкер может
  удалить секцию либо создать неоднозначное число её экземпляров.
- Формат `--version` в `codex` и `codex-code-mode-host` может разойтись. Прямое
  модульное покрытие сейчас закрепляет основной CLI; одинаковое поведение
  host-бинарника требует отдельной проверки при изменении его корневого парсера.
