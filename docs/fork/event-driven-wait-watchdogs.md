# Событийное ожидание фоновой работы

## Обзор

Эта карточка фиксирует единый fork-контракт пассивного ожидания для трёх
model-visible механизмов:

- пустого `write_stdin`, который ожидает фоновый терминальный процесс;
- `wait_agent`, который ожидает активность или завершение субагента;
- `functions.wait`, который ожидает завершение выполняющейся ячейки Code Mode.

Каждый механизм должен ожидать релевантное runtime-событие без периодического
polling со стороны модели и иметь настраиваемый watchdog timeout. Значение по
умолчанию для всех трёх механизмов равно `60_000` миллисекунд; конфигурация
должна позволять увеличить его, в частности до `600_000` миллисекунд.

Контракт реализуется этой fork-доработкой. Готовность подтверждается card-level
регрессиями и обновлением config schema из раздела «Проверки».

## Зачем это нужно

Возврат wait tool только по короткому timeout запускает новый вызов модели даже
тогда, когда состояние фоновой работы не изменилось. В большой сессии каждый
такой ход повторно передаёт модели весь накопленный контекст и создаёт большое
значение `cached_input_tokens` без нового результата.

Runtime уже получает события завершения процессов, ячеек Code Mode и активности
субагентов. TUI также может самостоятельно показывать длительность ожидания,
состояние фоновой работы и поступающий терминальный вывод. Поэтому отсутствие
события не должно превращаться в ход модели только ради сообщения о том, что
ничего не произошло.

Watchdog timeout остаётся необходим для обнаружения зависшей или зациклившейся
работы. Он является редкой границей повторной оценки состояния, а не интервалом
активного polling.

## Итоговый контракт

### Настройки и значения по умолчанию

| Механизм | Ключ конфигурации | По умолчанию | Пример десятиминутного ожидания |
| --- | --- | --- | --- |
| Пустой `write_stdin` | `background_terminal_wait_timeout_ms` | `60_000` | `600_000` |
| `wait_agent` | `[features.multi_agent_v2].default_wait_timeout_ms` | `60_000` | `600_000` |
| `functions.wait` | `[features.code_mode].default_wait_timeout_ms` | `60_000` | `600_000` |

Все значения задаются в миллисекундах. Если в вызове отсутствует
`timeout_ms`/`yield_time_ms`, используется соответствующее значение из итоговой
конфигурации. Явный аргумент вызова сохраняет существующий приоритет над
значением по умолчанию и проходит применимую проверку границ.

Для `wait_agent` сохраняются существующие
`min_wait_timeout_ms`/`max_wait_timeout_ms`. Стандартный
`max_wait_timeout_ms = 3_600_000` допускает как новое значение `60_000` по
умолчанию, так и пользовательское значение `600_000`. Конфигурация, в которой
`default_wait_timeout_ms` выходит за границы min/max, отклоняется вместо
молчаливого ограничения.

Для пустого `write_stdin` существующий `background_terminal_max_timeout`
остаётся верхней границей, а его значение по умолчанию повышается до `3_600_000`.
Явно заданная пользователем граница сохраняет приоритет. Если
`background_terminal_wait_timeout_ms` превышает её, конфигурация отклоняется с
понятной ошибкой; runtime не обрезает значение молча.

Новое значение пустого `write_stdin` по умолчанию не меняет интерактивный
непустой `write_stdin`: запись байтов в PTY должна сохранять короткое ожидание
ответа и существующую верхнюю границу.

### Причины пробуждения

Инструмент ожидания возвращает управление модели при первом из релевантных
событий:

1. Пользователь отправил новый ввод в активный turn (`Steer`). Это относится ко
   всем трём механизмам.
2. Для `wait_agent` поступило `InputQueueActivity::Mailbox`: сообщение, запрос
   внимания или завершение субагента.
3. Для пустого `write_stdin` завершился ожидаемый терминальный процесс.
4. Для `functions.wait` завершилась ожидаемая ячейка Code Mode либо сама ячейка
   выполнила явный `yield_control()`.
5. Истёк настроенный watchdog timeout.

Обычный терминальный вывод не завершает пустой `write_stdin`: runtime накапливает
ограниченный по размеру результат для tool output, а клиент получает потоковые
события независимо. Промежуточный вывод Code Mode также не должен будить модель
без явного yield.

### Поведение при `Steer` и timeout

- Новый пользовательский ввод не теряется и не потребляется самим wait tool. Он
  включается в ближайший вызов модели после завершения tool call.
- `Steer` и watchdog timeout не завершают фоновый процесс, субагента или ячейку
  Code Mode. Последующее ожидание продолжает наблюдать ту же работу.
- Tool output явно различает завершение/активность, `Steer` и timeout. Модель не
  должна выводить завершение работы из одного факта возврата wait tool.
- При одновременной готовности завершения и watchdog runtime предпочитает
  фактическое состояние терминала и не сообщает живую работу после уже
  полученного завершения.
- Прерывание терминального ожидания не теряет уже собранный вывод. Прерывание
  Code Mode wait не теряет вывод или завершение, которые должен получить
  следующий observer.

### Клиентский прогресс

Пока wait tool остаётся pending, TUI может без хода модели обновлять:

- прошедшее время;
- имя ожидаемого агента, команды или ячейки;
- состояние фоновой работы;
- потоковый терминальный вывод;
- подсказку о пользовательском прерывании.

Клиентский индикатор ожидания является достаточным heartbeat. Runtime не должен
будить модель только для генерации сообщения «работа всё ещё выполняется».

## Архитектурное решение

Три механизма сохраняют собственных владельцев жизненного цикла, но используют
одну семантику результата ожидания: завершение/активность, `steered` или
`timed_out`.
Общий helper допустим только для гонки ожидающего `Future`, уведомления `Steer` и
крайнего срока; он не должен объединять хранилище процессов, mailbox субагентов
и состояние ячеек Code Mode в новый центральный планировщик.

`Steer` публикуется через `InputQueue` как неразрушающее уведомление. Handler
ожидания подписывается на него для текущего состояния хода, но не извлекает
pending input. Это сохраняет порядок пользовательских сообщений и позволяет
обычному циклу хода добавить ввод в следующий Responses request.

Терминальный сборщик должен включить `Steer` в тот же цикл событий, который уже
наблюдает завершение процесса, уведомление о выводе и крайний срок. Отмена
внешнего `Future` после частичного извлечения недопустима, потому что локально
собранный вывод может быть потерян.

Code Mode wait должен корректно снять observer при `Steer`. Существующий runtime
ячейки обязан либо вернуть накопленный результат, либо сохранить его для
следующего observer; выполняющаяся ячейка продолжает работу.

Model-visible описания инструментов сообщают настроенное значение по умолчанию и
раннее событийное завершение, чтобы модель не реализовывала собственный короткий
polling поверх wait tool.

## Порядок повторения при переносе

1. Найти текущие handlers и model-visible описания `wait_agent`, `write_stdin` и
   `functions.wait`, а также runtime-владельцев mailbox субагентов, терминального
   процесса и ячейки Code Mode.
2. Проверить, какие события завершения и прогресса уже доступны в новом upstream;
   не заменять существующую сигнализацию новым polling loop.
3. Добавить `background_terminal_wait_timeout_ms` и
   `[features.code_mode].default_wait_timeout_ms`, изменить значение по умолчанию
   `[features.multi_agent_v2].default_wait_timeout_ms` на `60_000`.
4. Поднять стандартный `background_terminal_max_timeout` до `3_600_000`,
   сохранить явно заданную границу и отклонять
   `background_terminal_wait_timeout_ms`, если она эту границу превышает.
5. Материализовать итоговые значения по умолчанию и обновить config schema.
6. Различать отсутствующий timeout и явно переданное в вызове значение; не
   применять значение фонового терминала по умолчанию к непустому `write_stdin`.
7. Подключить неразрушающее уведомление `Steer` к терминальному ожиданию и
   ожиданию Code Mode.
8. Сохранить раннее завершение по завершению процесса или ячейки,
   `yield_control()` и `InputQueueActivity::Mailbox`.
9. Проверить гонки завершения, `Steer` и timeout, сохранность вывода и
   продолжение фоновой работы после `Steer` или timeout.
10. Обновить model-visible описания и регрессионные проверки.

## Риски и ограничения

- Большой watchdog откладывает автоматическую диагностику зависания, но не
  блокирует пользовательский `Steer` или прерывание.
- Короткий настроенный watchdog остаётся допустимым осознанным выбором, хотя
  создаёт дополнительные ходы модели и повторную передачу `cached_input_tokens`.
- Одно уведомление `Steer` могут одновременно наблюдать несколько подсистем; оно
  не должно потребляться одним wait handler или превращаться в mailbox activity.
- Терминальный вывод и вывод Code Mode должны сохраняться при любой гонке между
  завершением, `Steer` и timeout.
- Remote Code Mode обязан сохранять ту же семантику, что и локальный runtime;
  транспортный timeout не должен незаметно подменять настроенный watchdog.
- Настройки определяют значение по умолчанию отдельного tool call, а не общий
  предел времени жизни процесса, агента или ячейки.
- Повышение стандартного `background_terminal_max_timeout` только разрешает
  более длинное ожидание. Без явного per-call значения или нового
  `background_terminal_wait_timeout_ms` оно само по себе не увеличивает
  фактический timeout.
