# Fork card contract

Статус: `перенесено`.

Этот файл владеет назначением, содержанием и критериями готовности
`docs/fork/*.md` внутри skill-owned fork workflow.

## Роль карточки

`docs/fork/` хранит внутренние handoff-карточки кодовых fork-доработок. Эти
карточки не являются пользовательской документацией upstream Codex: они нужны,
чтобы будущий агент мог восстановить, перенести, проверить или откатить
fork-доработку без истории чата.

Карточка является источником текущего согласованного решения и описанием
реализации. Она фиксирует итоговый контракт, устройство доработки, owner-файлы,
порядок переноса, регрессионные проверки и действующие ограничения.

Карточка не является:

- стенограммой обсуждения;
- журналом миграций и запусков;
- историей сборок и установок;
- архивом исправленных ошибок;
- мета-отчётом о полноте самой карточки;
- кратким резюме коммита или простым списком изменённых файлов.

Подробности должны позволять воспроизвести доработку, но не должны сохранять
процесс, в котором это решение было получено.

## Изменение fork-контракта

Карточка фиксирует согласованный с пользователем fork-контракт. Общая просьба
мигрировать, перенести, проверить или починить карточку разрешает адаптировать
реализацию, но сама по себе не разрешает менять этот контракт.

Переход на новое upstream API не требует отдельного согласования, если
сохраняются прежние поведение и гарантии. В этом случае можно обновлять
owner-файлы, имена типов и методов, внутреннее устройство, call path, тестовый
harness, описание реализации и порядок повторения переноса.

Изменением fork-контракта считается добавление, удаление или изменение:

- наблюдаемого runtime-, model-visible-, CLI-, TUI-, app-server-, protocol- или
  tool-поведения;
- публичного API, config/schema-контракта, значений по умолчанию, ошибок,
  лимитов, precedence, порядка данных или совместимости;
- side effects, lifecycle- и retry-гарантий, обязательных инвариантов или
  границы ответственности доработки;
- ожидаемого результата регрессионных проверок, если меняется проверяемое
  поведение, а не только тестовый API или harness.

Upstream-изменение, новое правило проекта, конфликт с кодом, падение теста или
удобство реализации являются основанием предложить изменение контракта, но не
разрешением принять его. Если текущая задача пользователя не содержит точного
решения по такому изменению, его нужно отдельно согласовать. При сомнении считай
изменение контрактным, а не маскируй его синхронной правкой кода, тестов и
карточки.

## Достаточная подробность

Карточка должна явно описывать:

- зачем нужна доработка;
- какой текущий статус имеет доработка;
- какие файлы, crates, config keys, API surfaces, prompts, tests и цели сборки
  принадлежат доработке;
- итоговое runtime/model-visible/API/config/schema поведение;
- контракты, инварианты и ограничения, которые нельзя нарушать;
- устройство реализации и причины неочевидных архитектурных решений;
- порядок повторения переноса на новый upstream;
- card-level regression tests и исполняемую карту `fork-tests.v1`;
- действующие риски и открытые вопросы, если они есть.

Карточку обновляй, когда меняется хотя бы один из этих элементов. Очередной
успешный или неуспешный запуск тестов, сборки, установки либо migration gate сам
по себе не является причиной изменять карточку.

Не создавай обязательные заглушки `Нет` или `Не применимо` для необязательных
разделов. Если соответствующего содержания нет, раздел не нужен.

## Решения и обоснование

Итоговые решения описывай в `Итоговом контракте` и `Архитектурном решении`
обычным текстом или компактным списком. Не создавай таблицу принятых решений с
одинаковыми статусами: сама актуальная карточка уже означает, что описанное
решение принято.

Отклонённую альтернативу упоминай рядом с выбранным решением только тогда, когда
без этого нельзя понять важный инвариант, ограничение или причину архитектуры.
Не создавай отдельный исчерпывающий каталог альтернатив.

## Критерии готовности

Карточка считается готовой, если по ней можно без истории чата:

- понять пользовательскую цель и итоговое runtime/model-visible поведение;
- найти owner-файлы и понять роль каждого файла;
- восстановить API, tool spec, config, prompt, schema, defaults, примеры
  input/output и ошибки, если они относятся к доработке;
- понять устройство реализации и причины существенных архитектурных решений;
- повторить реализацию или перенос на новый upstream с чистого checkout;
- определить card-level regression tests и запустить их через skill-owned
  workflow;
- понять действующие риски, ограничения и открытые вопросы;
- проверить соответствие карточки текущему коду обычным review.

## Структура карточки

Для активной кодовой fork-доработки используй следующие разделы:

- `Обзор`;
- `Зачем это нужно`;
- `Карта файлов`;
- `Итоговый контракт`;
- `Архитектурное решение`;
- `Порядок повторения при переносе`;
- `Проверки`;
- `Риски и ограничения`.

`Открытые вопросы` добавляй только при наличии действующих вопросов.

Не создавай в owner-карточках следующие legacy-разделы:

- `Согласованные решения`;
- `Отклоненные альтернативы`;
- `Смысловое покрытие`;
- `Исторические результаты`;
- `Известные падения и пропуски`;
- `Runtime, сборка и установка`;
- `Проверка покрытия`.

## Контракт раздела `Проверки`

Раздел `Проверки` описывает только обязательную исполняемую карту текущей
доработки. Он не является журналом запусков или command runbook.

Для автоматизированных card-level regression tests карточка должна содержать
machine-readable блок `fork-tests.v1`. Поле `purpose` кратко и предметно
описывает проверяемое поведение, а `argv` хранит внутренний вызов, которым
владеет `fork tests`. Опциональное поле `platforms` ограничивает запись одним
или несколькими значениями `linux`, `macos`, `windows`; отсутствие поля означает
все поддерживаемые платформы. На несовпадающей платформе runner прозрачно
пропускает запись и не считает её ошибкой. Не дублируй те же сведения отдельной
таблицей смыслового покрытия.

Если автоматизированная card-level проверка отсутствует, раздел должен содержать
машинно проверяемое исключение `manual-required` или `not-applicable` с
причиной.

Дополнительный skill-owned gate, например `fork generators` или
`fork build-fast`, указывай только когда он необходим для воспроизведения или
проверки конкретной доработки. Не добавляй строки `not-applicable` для
неотносящихся к ней gates.

Прямые `just`/`cargo` команды и workflow-вызовы не должны появляться в
человекочитаемом тексте карточки как инструкция. Внутренний argv допустим только
как данные блока `fork-tests.v1`. Если требуемого skill-owned владельца нет,
сначала обнови workflow или зафиксируй blocker вне owner-карточки.

## Результаты запусков и история

Результаты конкретных тестов, сборок, установок и migration gates не принадлежат
owner-карточке:

- текущий gate status хранится в JSON migration map;
- полный stdout/stderr и диагностические подробности принадлежат skill-owned
  логам;
- хронология изменений принадлежит Git;
- итог конкретного рабочего прохода сообщается в рабочем отчёте.

Если запуск выявил новое постоянное current-state сведение о реализации,
архитектурное ограничение, регрессионный сценарий или действующий риск без
изменения fork-контракта, обнови соответствующий нормативный раздел карточки.
Необходимость изменить контракт требует отдельного решения пользователя по
правилам раздела `Изменение fork-контракта`. Сам факт запуска, его дата, версия
бинарника, размер, hash, путь установки или уже исправленное падение в карточку
не переносятся.
