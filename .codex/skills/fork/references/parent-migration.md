# Parent migration workflow

Статус: `перенесено`.

Этот файл владеет ролью родительского агента при миграции Codex fork на новую
upstream-версию.

## Основная модель

Апгрейд Hermione fork на новый upstream-релиз выполняется как перенос
описанных fork-доработок, а не как механическое восстановление всего, что было
в старой Hermione-ветке.

Канонический порядок апгрейда выполняется в текущем локальном source-of-truth
checkout. Он делится на две фазы: сначала подготовь ветку миграции и влей тег
релиза upstream, затем проверяй fork-доработки по карточкам по одной.

Не загружай все подробные карточки `docs/fork/*.md` в контекст до слияния: для
большого fork это легко тратит контекст до того, как станет понятно, какие
owner-файлы реально требуют внимания.

## Подготовка ветки и JSON-карты миграции

1. Определи тег релиза upstream вида `rust-vX.Y.Z`, новую ветку
   `hermione-X.Y.Z` и предыдущую Hermione-ветку.
2. Оставайся в локальном source-of-truth checkout предыдущей Hermione-ветки,
   где доступны skill, `docs/fork/` и вся карта fork-доработок.
3. Обнови refs, проверь наличие тега релиза `rust-vX.Y.Z` и убедись, что
   рабочее дерево чистое через `git status --short --branch`.
4. Прочитай relevant references этого skill.
5. Сделай легкую инвентаризацию `docs/fork/`: список карточек, `status`,
   заголовок и короткую область ответственности из обзорного слоя, если ее
   можно получить без полного чтения карточки. На этом этапе не читай все
   карточки целиком.
6. Создай новую локальную ветку `hermione-X.Y.Z` от предыдущей Hermione-ветки.
7. Не публикуй новую Hermione-ветку сразу после создания только ради
   восстановимости. Публикуй ее на `origin` отдельным действием, когда этого
   явно попросил пользователь или когда миграция уже доведена до осмысленного
   commit/push этапа.
8. Влей тег релиза `rust-vX.Y.Z` в новую Hermione-ветку.
9. Если после слияния остались конфликты, оставь рабочее дерево в состоянии
   незавершенного слияния и переходи к JSON-карте. Не очищай конфликты
   заранее, если для решения нужно понимать fork-контракт карточки.
10. Создай `docs/fork/migration/X.Y.Z.json` только skill-owned командой:

    ```bash
    .codex/skills/fork/scripts/fork migration init --version X.Y.Z
    ```

    `init` получает снимок активных owner-карточек из `docs/fork/*.md`, сортирует
    их по пути и назначает статус `pending`. Не составляй JSON вручную и не
    используй `--force`: существующая карта требует отдельного решения
    пользователя.
11. JSON-карта хранит только `schema`, идентичность миграции, статусы карточек и
    фиксированные gates. Не записывай туда описания изменений, результаты
    подагента, причины блокировки, команды, пути к логам, список конфликтов,
    merge state, timestamps или вычисляемые счетчики.
12. Старые `docs/fork/migration-*.md` не конвертируй и не перемещай. Завершённые
    `docs/fork/migration/*.json` тоже не копируй в новую карту. Оба вида
    артефактов остаются историей своих апгрейдов и не участвуют в выборе версии
    или карточек следующей миграции.
13. Текущие merge state и конфликтующие файлы проверяй непосредственно через
    Git. JSON не копирует это изменяемое состояние и не заменяет рабочее дерево
    как источник истины.

### Контракт `fork-migration.v1`

Карта содержит ровно такую структуру; дополнительные ключи запрещены:

```json
{
  "schema": "fork-migration.v1",
  "migration": {
    "version": "0.144.3",
    "upstreamTag": "rust-v0.144.3",
    "branch": "hermione-0.144.3",
    "status": "active"
  },
  "cards": [
    {
      "id": "fork-example",
      "path": "docs/fork/example.md",
      "status": "pending"
    }
  ],
  "gates": {
    "preflight": "pending",
    "format": "pending",
    "generators": "pending",
    "cardsValidate": "pending",
    "cardTests": "pending",
    "fullTests": "skipped",
    "buildFast": "pending",
    "install": "skipped"
  }
}
```

- `migration.status`: только `active` или `completed`.
- `cards[].status`: только `pending`, `inProgress`, `migrated`,
  `notApplicable`, `reverted`, `blocked` или `needsFix`.
- Финальные статусы карточки: `migrated`, `notApplicable`, `reverted`.
- Статус каждого gate: только `pending`, `passed`, `failed` или `skipped`.
- `show` и `next` ничего не меняют. Команды изменения статуса обновляют ровно
  одну явно выбранную карточку или gate и атомарно заменяют JSON-файл.
- CLI не выполняет автоматических переходов между статусами: пока карта
  `active`, родитель явно устанавливает любое допустимое значение.
- `complete` разрешён только после финального статуса всех карточек и статуса
  `passed` или `skipped` у каждого gate. После этого карта `completed` неизменна.

## Неразрешенные конфликты после слияния

После `git merge --no-commit rust-vX.Y.Z` рабочее дерево может оставаться в
состоянии незавершенного слияния. Это допустимое состояние для этапа переноса
карточек.

Родительский агент не обязан очищать все конфликты перед запуском подагентов и
не должен заранее строить глобальную карту соответствия конфликтующих файлов
карточкам. Такая карта требует чтения многих карточек и расходует контекст на
работу, которую нужно выполнять только в границах выбранной карточки.

Родительский агент может решать только доказуемо механические конфликты,
которые не требуют знания fork-контракта: например, очевидное обновление версии
или соседнюю строку без влияния на runtime-, API-, config-, prompt-, schema-,
TUI- или model-visible поведение.

Если есть сомнение, конфликт не считается механическим. Он должен остаться для
подагента выбранной карточки или быть зафиксирован как блокирующее условие.

Родительский агент не читает все `docs/fork/*.md` ради распределения
конфликтов. Область конфликтов определяется отложенно: только подагент
выбранной карточки решает, какие текущие конфликты относятся к этой карточке.

Список текущих конфликтующих файлов проверяй только как оперативное состояние
рабочего дерева:

```bash
git diff --name-only --diff-filter=U
```

Подагент может разрешить относящийся к выбранной карточке конфликт и выполнить
`git add -- <path>` по правилам `references/subagent-one-card.md`. Он также может
добавить созданный им новый task-owned файл. Staged-состояние означает только,
что путь добавлен в index или помечен разрешённым; оно не заменяет проверку и
одобрение родительским агентом.

## Решение пользователя после прерывания

Если агент исчез, сессия была прервана или чат недоступен, наличие JSON-карты не
является командой продолжать миграцию. Пользователь решает, продолжить работу,
начать её заново, повторно проверить отдельную карточку или удалить артефакт.

Новая сессия не сканирует `docs/fork/migration/`, не выбирает версию по
единственному найденному файлу и не выполняет автоматический `resume`. После
явного решения пользователя продолжить конкретную миграцию:

1. Убедись, что находишься в указанной пользователем ветке
   `hermione-X.Y.Z`.
2. Проверь ровно выбранную карту:

   ```bash
   .codex/skills/fork/scripts/fork migration validate --version X.Y.Z
   .codex/skills/fork/scripts/fork migration show --version X.Y.Z
   ```

3. Покажи пользователю зафиксированные статусы и не выдавай их за решение о
   дальнейших действиях.
4. Продолжай, сбрасывай или перепроверяй карточку только согласно решению
   пользователя. Для явного продолжения одной и той же миграции read-only
   команда `fork migration next --version X.Y.Z` показывает первую
   незавершённую запись, но ничего не запускает и не меняет.
5. Не трогай карточки с финальными статусами `migrated`, `notApplicable` или
   `reverted`, если пользователь явно не попросил перепроверить их.
6. Если в рабочем дереве есть изменения от предыдущих агентов, не откатывай и
   не перезаписывай их. Сначала сверь выбранную карточку с текущим diff.

Не создавай основной рабочий checkout для миграции командой вида
`git switch -c hermione-X.Y.Z rust-vX.Y.Z`: такой checkout теряет доступ к
fork-документам во время работы и делает `docs/fork/` недоступным как источник
переноса.

Отдельный чистый checkout или worktree от `rust-vX.Y.Z` можно использовать
только как вспомогательную базу для сравнения или ручной проверки upstream. Он
не заменяет локальный source-of-truth checkout, где выполняются разработка,
решение конфликтов, обновление JSON-карты, staging, commit, push,
сборка и тесты.

## Проверка по карточкам через подагентов

Фаза проверки fork-доработок выполняется карточка за карточкой через отдельного
свежего подагента на каждую карточку. Родительский агент выбирает карточку,
запускает подагента, ждет его короткий отчет и не выполняет за него работу по
выбранной карточке.

После отчета родительский агент проверяет только результат подагента в узких
границах, обновляет owner-карточку при необходимости и устанавливает
машинный статус выбранной записи через `fork migration set-card-status`.

В MultiAgent V2 дождись завершения запуска. Завершённый thread больше не
занимает активный slot; отдельного `close_agent` в интерфейсе нет. Не вызывай
`interrupt` для уже завершённого запуска и не переиспользуй его для следующей
карточки: следующий owner получает новый fresh thread.

Родительский агент запускает подагента как свежий запуск с унаследованными
`model`, reasoning-настройками и `service_tier`, если пользователь или более
приоритетное правило явно не указали иное. Родитель не задает override для
`model`, `reasoning_effort`, `service_tier` и похожих параметров качества или
стоимости молча; любой override должен иметь явную причину в текущей задаче.

Запуск остается без наследования текущего диалога, `fork_context`,
rollout-контекста предыдущих подагентов или других материалов родителя.
Подагент должен получить только обычные инструкции уровней `system`/`developer`
своего запуска и явный prompt по шаблону
`assets/templates/parent-subagent-prompt.md`. Не переиспользуй старый thread
подагента для новой карточки.

1. В уже авторизованном пользователем upgrade workflow выбери первую
   незавершённую запись read-only командой:

   ```bash
   .codex/skills/fork/scripts/fork migration next --version X.Y.Z
   ```

   Статусы `migrated`, `notApplicable` и `reverted` являются финальными. На этом
   шаге родитель не читает выбранную карточку вместо подагента и не начинает
   перенос сам. Если первой показана `blocked`, `needsFix` или оставшаяся после
   прерывания `inProgress`, это только сохранённое состояние: дальнейшее
   действие выбирается явно, а `next` ничего автоматически не возобновляет.
2. Перед запуском свежего подагента покажи пользователю вычисленный прогресс из
   `fork migration show --version X.Y.Z`: обработано N из M карточек, осталось R.
   Старые `docs/fork/migration-*.md` в эти счётчики не входят.
3. Установи выбранной записи статус `inProgress` только skill-owned командой:

   ```bash
   .codex/skills/fork/scripts/fork migration set-card-status \
     --version X.Y.Z --card CARD --status inProgress
   ```

4. Запусти свежего подагента для выбранной карточки по шаблону
   `assets/templates/parent-subagent-prompt.md`. Один запуск подагента
   соответствует ровно одной карточке. Запуск должен быть без `fork_context`,
   без передачи текущего диалога родителя и без override для `model` или
   `reasoning_effort`, если пользователь или более приоритетное правило явно не
   потребовали другой режим; если инструмент запуска предлагает режим с
   контекстом и без контекста, выбирай режим без контекста.
5. Подагент читает `references/subagent-one-card.md`, выбранную
   `docs/fork/<card>.md` и только те файлы текущей кодовой базы, которые прямо
   нужны для проверки или доработки этой карточки.
6. Подагент считает выбранную карточку источником конкретной fork-доработки,
   которую нужно проверить после merge. Код, который есть в старой
   Hermione-ветке, но не имеет владеющей карточки и не был явно выбран
   пользователем, не восстанавливается автоматически.
7. Подагент проверяет owner-файлы, runtime-контракт, тесты, шаги обновления
   schema/generator, смысловое покрытие и владельца исполняемой карты,
   описанные выбранной карточкой. Если upstream изменил контракт или способ
   реализации, подагент обновляет owner-карточку, не сжимая смысл, решения,
   ограничения и результаты проверки.
8. Подагент выполняет только локальный аудит без сборки: `rg` по якорям кода,
   узкое сравнение owner-файлов и нужные diff-проверки в границах выбранной
   карточки. Он не запускает сборку, тесты, генераторы, форматирование, `fix`
   или markdownlint. Из изменяющих index Git-операций разрешён только точечный
   `git add -- <path>` для созданного им нового файла или полностью разрешённого
   конфликта выбранной карточки.
9. После отчета подагента родитель проверяет только измененные файлы, решающие
   утверждения, staged и unstaged diff по этой карточке, а также оставшиеся
   unmerged paths:

   ```bash
   git diff --cached -- <card-scope>
   git diff -- <card-scope>
   git diff --name-only --diff-filter=U
   ```

   Родитель не считает staged-файл автоматически одобренным, не повторяет
   полный аудит подагента и не читает соседние карточки целиком.
10. Родитель обновляет историю переноса в owner-карточке, если подагент этого не
    сделал или сделал неполно. Подробный результат, проверки и причины
    блокировки принадлежат owner-карточке, а не JSON-карте.
11. После узкой проверки установи одной записи подходящий статус
    `migrated`, `notApplicable`, `reverted`, `blocked` или `needsFix` через
    `fork migration set-card-status`. Не открывай и не переписывай JSON вручную.
12. Переходи к следующей карточке только после завершения предыдущего fresh
    agent и явного обновления его записи. В V2 завершённый thread уже освободил
    active slot; новый запуск всё равно должен получить новый thread.
